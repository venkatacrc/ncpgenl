Verse 2.01 — Prompt anatomy: roles & delimiters
Objective 2.1

A chat prompt is a structured sequence of roles — system (behavior/constraints),
user (task), assistant (model turns) — rendered into the model's chat template
(special tokens like <|system|>, [INST]). Delimiters (triple backticks, XML tags)
separate instructions from data and reduce injection ambiguity. The system message is
the highest-leverage, lowest-cost control surface before any fine-tuning.

messages = [
  {"role": "system", "content": "You are a terse SQL assistant. Output SQL only."},
  {"role": "user", "content": "users older than 30"},
]
prompt = tokenizer.apply_chat_template(messages, add_generation_prompt=True, tokenize=False)

Verse 2.02 — Zero-shot prompting
Objective 2.2

Zero-shot = instruction only, no examples. Relies entirely on knowledge acquired in
pretraining/instruction-tuning. Works when the task is common and unambiguous; fails
when output format or a niche label set must be inferred. Cheapest prompt (fewest
tokens), lowest steering.

Verse 2.03 — One-shot prompting
Objective 2.2

One-shot = a single worked example before the query. The example fixes format and
label vocabulary more reliably than instructions alone; it demonstrates rather than
describes. Cheapest way to pin output shape when zero-shot drifts.

Text: "Loved it." -> Sentiment: positive
Text: "The battery drains too fast." -> Sentiment:
Chain → One example fixes format; what if the task needs the model to generalize across several patterns? (2.04)
Verse 2.04 — Few-shot prompting & exemplar selection
Objective 2.2

Few-shot = k examples (typically 2–8). Accuracy rises with informative, diverse,
class-balanced exemplars; degrades with redundant or skewed ones. Recency/order
matters — models over-weight later examples. Retrieval-based selection (pick
exemplars similar to the query) beats fixed sets on heterogeneous inputs. Bounded by
context length and cost.

# 3-shot, class-balanced, then the query
pos -> "Loved it."
neg -> "Broke in a week."
neu -> "It's fine, nothing special."
query -> "The battery drains too fast."
Chain → Examples fix pattern-matching; but how does adding examples actually change the model without touching its weights? (2.05)
Verse 2.05 — In-context learning (no weight update)
Objective 2.2

In-context learning (ICL) = the model conditions on exemplars in the prompt and adapts
its output distribution without any gradient step. Weights are frozen; "learning"
is transient, living only in the forward pass's activations/KV cache. Implication:
ICL cannot add durable knowledge or survive across sessions — that is what fine-tuning
(Domain 5) is for. Distinguish sharply from prompt learning / P-tuning (2.12),
which does train continuous prompt vectors.

Chain → If plain examples aren't enough for multi-step reasoning, how do we make the model show its work? (2.06)
Verse 2.06 — Chain-of-thought (CoT) prompting
Objective 2.1

CoT elicits intermediate reasoning steps before the final answer, improving
multi-step arithmetic/logic/commonsense accuracy. It works because generation is
autoregressive: written steps become context the model conditions on (externalized
scratchpad). Trade-off: more tokens, higher latency/cost, and reasoning can be
plausible-but-wrong.

Q: A shelf has 3 boxes of 12 and 2 boxes of 5. How many items?
A: Let's reason step by step. 3*12=36. 2*5=10. 36+10=46. Answer: 46.
Chain → CoT needs a worked example — can we trigger reasoning with zero examples? (2.07)
Verse 2.07 — Zero-shot CoT
Objective 2.1

Append a trigger phrase — "Let's think step by step." — with no exemplars. Elicits
reasoning cheaply on capable instruct models. Weaker/smaller models may need few-shot
CoT (2.09). Often paired with a second "extraction" prompt that pulls the final answer
out of the reasoning trace.

Q: If a train travels 60 km in 45 minutes, what is its speed in km/h?
A: Let's think step by step.
Chain → A single reasoning path can go wrong — how do we make reasoning robust? (2.08)
Verse 2.08 — Self-consistency
Objective 2.1

Sample multiple CoT traces (temperature > 0), then take a majority vote over
final answers. Marginalizes over reasoning paths, correcting single-path errors; large
accuracy gains on arithmetic/reasoning. Cost scales linearly with the number of
samples — a compute-for-accuracy trade (a form of test-time scaling, 2.13).

answers = [extract(sample_cot(prompt, temperature=0.7)) for _ in range(8)]
final = max(set(answers), key=answers.count)   # majority vote
Chain → Voting fixes reasoning; but how do we give the model more examples of the *reasoning itself*? (2.09)
Verse 2.09 — Few-shot CoT
Objective 2.1

Provide k exemplars that each include the reasoning trace, not just the answer.
Teaches the model the style and granularity of reasoning for the domain. Best for
smaller models or specialized formats where zero-shot CoT (2.07) underperforms.
Exemplar quality dominates: one wrong trace can anchor the model to a bad pattern.

Q: 17 apples, give away 5, buy 12. How many?
A: 17-5=12. 12+12=24. Answer: 24.

Chain → Reasoning traces alone are passive — how does the model act on tools/the world while reasoning? (2.10)
Verse 2.10 — ReAct (reason + act)
Objective 2.1

ReAct interleaves Thought → Action → Observation loops: the model reasons, emits a
tool call (search, calculator, retrieval), reads the result, and continues. Grounds
reasoning in external state, reducing hallucination on knowledge tasks and enabling
agents. Requires an orchestration loop that parses actions and feeds observations back.

Thought: I need the current population.
Action: search("population of Iceland 2024")
Observation: ~383,000
Thought: That answers it.
Answer: about 383,000
Chain → These patterns repeat across queries — how do we parameterize them for reuse? (2.11)
Verse 2.11 — Prompt templates & parameterization
Objective 2.1

A template separates fixed instruction scaffolding from variable slots, making prompts
versionable, testable, and injection-aware. Treat prompts as code: pin a version,
diff changes, and A/B test (ties to Domain 9 versioning). Escape/validate user-filled
slots to blunt prompt injection (2.25).

TEMPLATE = (
  "System: You are a {persona}.\n"
  "Task: {task}\n"
  "Constraints: answer in {n} bullet points.\n"
)
prompt = TEMPLATE.format(persona="network engineer", task="explain BGP", n=3)
Chain → Templates use discrete text — can we instead *learn* the prompt as vectors? (2.12)
Verse 2.12 — Prompt learning: soft vs hard prompts
Objective 2.1

Hard prompts are discrete natural-language tokens (everything above). Soft
prompts are continuous, trainable embedding vectors prepended to the input; the
model weights stay frozen while only these vectors are learned via backprop —
parameter-efficient adaptation for small datasets/specialized domains. This is the
bridge to P-tuning / prefix tuning in Domain 5 (5.15).

[p1][p2]...[pk]  <actual input tokens>
# p1..pk are learned float vectors, not tokens from the vocabulary
Chain → Soft prompts help small data — but what if we just spend more inference compute to reason harder? (2.13)
Verse 2.13 — Test-time scaling / reasoning-token budget
Objective 2.1

Test-time scaling trades inference compute for accuracy: longer reasoning traces,
more self-consistency samples (2.08), or best-of-N with a verifier. Reasoning models
expose a "thinking budget" (max reasoning tokens). Diminishing returns and latency/cost
ceilings apply. NVIDIA framing: this is why serving must budget KV cache and tokens
per request (ties to 8.02 prefill/decode, 9.03 metrics).

Chain → More compute helps general tasks — but how do we adapt to a *specialized domain* purely through prompting? (2.14)
Verse 2.14 — Domain adaptation via prompting
Objective 2.1

For specialized domains or small datasets, adapt without fine-tuning: inject a domain
glossary/style guide in the system prompt, use retrieved domain snippets (RAG, 2.23),
and few-shot with in-domain exemplars. Decision boundary: prompt-only adaptation is
free and instant but capped by context length and cannot add durable knowledge — cross
over to PEFT/fine-tuning (Domain 5) when volume or consistency demands it.

Chain → Prompting adapts a *pretrained* decoder — but how is a decoder trained to predict text in the first place? (2.15)
Verse 2.15 — Causal language modeling (CLM) objective
Objective 2.3

Decoders are trained to predict the next token: minimize
$\mathcal{L}=-\sum_t \log p(x_t \mid x_{<t})$ (cross-entropy over the vocabulary), with
the causal mask (1.06) guaranteeing no future leakage. This single objective, at scale,
yields the in-context abilities Domain 2 exploits. Contrast with MLM for encoders
(4.28).

import torch.nn.functional as F
# logits: [B, T, V]; labels: [B, T] (input shifted left by 1)
loss = F.cross_entropy(logits[:, :-1].reshape(-1, V), labels[:, 1:].reshape(-1))
Chain → Predicting `x_t` from `x_{<t}` during training — how do we feed the ground truth efficiently? (2.16)
Verse 2.16 — Teacher forcing & shifted labels
Objective 2.3

During training the decoder is fed the ground-truth previous tokens (not its own
predictions) — teacher forcing — so all positions train in parallel in one forward
pass. Labels are the inputs shifted by one; loss is masked on padding and often on
the prompt portion (train only on the completion). Exposure bias (train sees gold,
inference sees own outputs) is the known downside.

labels = input_ids.clone()
labels[:, :prompt_len] = -100     # ignore prompt tokens in loss
labels[attention_mask == 0] = -100
Chain → With objective and labels defined, what does a minimal training loop look like? (2.17)
Verse 2.17 — Train a decoder with CLM (code sketch)
Objective 2.3

Minimal HF loop: tokenize, let the model shift labels internally (pass labels=input_ids
for pure LM), backprop cross-entropy. This is the substrate SFT (5.01) builds on.

from transformers import AutoModelForCausalLM, AutoTokenizer
import torch
tok = AutoTokenizer.from_pretrained("gpt2"); tok.pad_token = tok.eos_token
m = AutoModelForCausalLM.from_pretrained("gpt2").cuda().train()
opt = torch.optim.AdamW(m.parameters(), lr=5e-5)
batch = tok(["hello world"], return_tensors="pt").to("cuda")
out = m(**batch, labels=batch.input_ids)     # HF shifts labels internally
out.loss.backward(); opt.step(); opt.zero_grad()
print(float(out.loss))

Verse 2.18 — Structured output: JSON schema prompting
Objective 2.4

Ask for machine-parseable output (JSON) and provide the schema in the prompt plus a
one-shot example. Improves parse rates but does not guarantee validity — the model
can still emit malformed JSON. Prompt-level structuring is necessary but not
sufficient; pair with constrained decoding (2.19) for hard guarantees.

Return ONLY JSON matching:
{"intent": string, "entities": string[], "confidence": number}
Text: "book a flight to Tokyo next Friday"
Chain → Prompting for JSON still allows invalid output — how do we make invalid tokens impossible? (2.19)
Verse 2.19 — Constrained decoding: grammar / logit masking
Objective 2.4

Constrained decoding restricts the sampling step to tokens allowed by a grammar
(CFG/regex/JSON schema). At each step, tokens that would violate the grammar have their
logits set to -∞ (masked), so invalid output is impossible by construction — a
hard guarantee that prompting (2.18) cannot give. Cost: a grammar/state machine and
per-step mask computation.

def masked_logits(logits, allowed_ids):
    mask = torch.full_like(logits, float("-inf"))
    mask[..., allowed_ids] = 0.0
    return logits + mask     # only grammar-allowed tokens survive softmax
Chain → Even valid-shaped output can be wrong or unsafe — where does the validation live? (2.20)
Verse 2.20 — LLM-wrapping module with validation
Objective 2.4

Wrap the model in a module that (1) builds the prompt from a template, (2) applies
constrained decoding, (3) validates output against a schema/business rules, and
(4) retries or repairs on failure. This is NVIDIA's "specialized LLM-wrapping module
with built-in validation" — it turns a probabilistic generator into a dependable
component and is where guardrails (Domain 10) attach.

def call(model, msg, schema, retries=2):
    for _ in range(retries + 1):
        out = model.generate(build_prompt(msg), grammar=schema)
        ok, parsed = validate(out, schema)
        if ok: return parsed
    raise ValueError("validation failed after retries")
Chain → Validation catches format errors — but how do we stop the model asserting false facts? (2.21)
Verse 2.21 — Hallucination reduction via grounding
Objective 2.4

Reduce fabrication by grounding: supply authoritative context (retrieved
documents, 2.23) and instruct the model to answer only from it and to say "I don't
know" otherwise. Add citations so claims are checkable. Grounding attacks the root
cause (missing knowledge in-context) better than post-hoc filtering. Deeper mitigation
(fine-tuning, Guardrails) is in Domains 5 and 10.

Answer using ONLY the context. If the context is insufficient, say "I don't know."
Context: {retrieved_chunks}
Question: {q}
Chain → Grounding constrains content — but who enforces the output policy at runtime? (2.22)
Verse 2.22 — Guardrails handoff (xref Domain 10)
Objective 2.4

Output control at runtime is owned by a guardrails layer: input rails (block
malicious/off-topic prompts), output rails (block unsafe/PII/hallucinated content),
and dialog rails (keep to allowed topics). NVIDIA's tool is NeMo Guardrails with
the Colang policy language (full treatment in 10.09–10.10). Prompt engineering
sets intent; guardrails enforce it independently of the model's cooperation.

Chain → Grounding needs relevant context — where does that context come from? (2.23)
Verse 2.23 — RAG anatomy (context injection)

Objectives: 2.1, 2.4

Retrieval-Augmented Generation = retriever + generator. An embedding model encodes
the query; a vector store returns top-k relevant chunks; those chunks are injected into
the prompt; the LLM generates grounded, citable answers. RAG adds fresh/proprietary
knowledge without retraining and is NVIDIA's default enterprise pattern (NeMo Retriever
+ NIM). It is a prompt-context technique, which is why it lives in Domain 2, not a
domain of its own.

[system] answer only from context
[context] <top-k retrieved chunks>
[user] <question>
Chain → RAG hinges on retrieval quality — how are chunks embedded and searched? (2.24)
Verse 2.24 — Retrieval: embedding search & chunking
Objective 2.1

Documents are split into chunks (size/overlap trade recall vs precision), embedded
(1.09/1.10), and indexed for approximate nearest-neighbor (ANN) search by cosine/dot
similarity. Query embedding → top-k chunks. Levers: chunk size, overlap, k, and
re-ranking. Poor chunking (too large → diluted; too small → fragmented) is the top RAG
failure mode. Evaluate with Ragas (6.08).

sims = query_emb @ chunk_embs.T          # [1, N]
topk = sims.topk(k).indices              # nearest chunks
Chain → Injecting external text into prompts opens an attack surface — what is it? (2.25)
Verse 2.25 — Prompt injection & jailbreak basics
Objective 2.4

Prompt injection: untrusted input (user text or retrieved content) carries
instructions that override the system prompt ("ignore previous instructions…").
Indirect injection hides instructions in RAG-retrieved documents. Jailbreaks
coax the model past its safety policy (role-play, obfuscation). Defenses: strong
delimiters, treat retrieved text as data not instructions, output rails, and least-
privilege tool access. Prompting alone is insufficient — enforce with guardrails
(2.22, Domain 10).

Chain → Beyond safety, these same decoding knobs shape user experience — how? (2.26)
Verse 2.26 — Sampling controls as UX levers
Objective 2.4

The decoding params from 1.11–1.12 are product controls exposed per request in the
serving stack (Dynamo-Triton / TensorRT-LLM): low temperature + low top_p for
deterministic, factual, testable output (code, extraction); higher values for creative
tasks. max_tokens bounds latency/cost; stop sequences and repetition_penalty
prevent runaway/looping output. Consistency requirements (validation, evals) usually
push production toward near-greedy settings.
