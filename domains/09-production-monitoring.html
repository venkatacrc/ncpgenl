The 14 Verses

Verse 9.01 — Monitoring stack (Prometheus + Grafana)
Objective 9.1

Prometheus scrapes time-series metrics from the Triton /metrics endpoint (port
8002, 8.17) and other exporters (DCGM-Exporter for GPU telemetry); Grafana
visualizes dashboards and drives alerting. This pull-based stack is NVIDIA's default for
LLM serving observability. Instrument before launch; you cannot debug what you don't
measure.

Chain → With a stack in place, which metrics actually matter? (9.02)
Verse 9.02 — Golden signals & LLM metrics
Objective 9.1

Classic golden signals: latency, traffic, errors, saturation. LLM-specific:
TTFT, TPOT/inter-token latency, tokens/sec throughput, queue depth,
KV-cache utilization, GPU util/memory (DCGM), and quality proxies (refusal rate,
guardrail triggers, user feedback). Track percentiles (p50/p95/p99), not means
(6.12). These feed SLOs (9.03).

Chain → Metrics need targets — how do we set them? (9.03)
Verse 9.03 — SLIs, SLOs & error budgets
Objective 9.1
  • SLI (indicator): a measured metric, e.g. "p99 TTFT" or "success rate."
  • SLO (objective): the target, e.g. "p99 TTFT < 500 ms, 99.9% of the time."
  • Error budget: 1 − SLO — the allowed failure amount; when exhausted, freeze
    risky changes and prioritize reliability.

SLOs turn raw metrics into actionable reliability targets and gate releases (ties to
9.13). Alert on SLO burn rate, not every blip.

Chain → Metrics tell you *that* something broke — how do we find *why*? (9.04)
Verse 9.04 — Logging, tracing & observability
Objective 9.2

The three pillars: metrics (aggregate trends), logs (discrete events — prompts,
errors, guardrail hits, with PII handling), traces (a request's path across services
— tokenizer → retriever → model, via OpenTelemetry). Together they enable root-cause
analysis. For LLMs, log prompt/response metadata (not raw PII), latencies per stage, and
token counts. Correlate by request/trace ID.

Chain → Logs are noisy — how do we surface the anomalies automatically? (9.05)
Verse 9.05 — Anomaly detection
Objective 9.2

Detect deviations automatically: threshold/static alerts (p99 > SLO), statistical
methods (z-score, EWMA, seasonal decomposition), and ML detectors for multivariate
signals. Alert on rate of change and burn rate, and reduce noise with
deduplication/grouping. For LLMs, watch for spikes in error rate, latency, refusal/
guardrail-trigger rate, and drift in input/output distributions (9.06). Tune to
avoid alert fatigue (missed real incidents).

Chain → A common silent failure is the world changing under the model — what is that? (9.06)
Verse 9.06 — Drift: data vs concept
Objective 9.2
  • Data (covariate) drift: the input distribution changes (new topics, languages,
    slang) while the target mapping holds.
  • Concept drift: the input→output relationship itself changes (what counts as
    "spam" evolves).

Detect via distribution distances (PSI, KL, embedding-space monitoring) on inputs and
outputs. Drift silently degrades quality with no error thrown → triggers retraining
(9.10). This is the top cause of "the model got worse over time."

Chain → Drift signals degradation vs a baseline — how do we benchmark against prior versions? (9.07)
Verse 9.07 — Continuous benchmarking & regression
Objective 9.3

Periodically re-score the deployed model on a fixed golden eval set (reusing the
Domain 6 harness) and compare to prior versions to catch regressions in quality/
latency/cost before users do. Automate in CI/CD and on a schedule; store versioned
results. A regression beyond threshold blocks promotion or triggers rollback. Complements
live metrics (which measure behavior, not correctness).

Chain → To compare versions safely in production, how do we roll them out? (9.08)
Verse 9.08 — Canary, shadow & A/B deployments
Objective 9.3
  • Canary: route a small % of live traffic to the new version, watch metrics, ramp up
    if healthy, roll back if not.
  • Shadow: send a copy of traffic to the new version without returning its responses
    — compare offline, zero user risk.
  • A/B: split traffic to measure a business/quality metric difference statistically.

Serve multiple versions simultaneously via the model repo version policy (8.18).

Chain → These strategies need a clean rollback — how is that guaranteed? (9.09)
Verse 9.09 — Rollback & safe deploy
Objective 9.3

Safe deployment requires fast, reliable rollback: keep the previous version loaded/
reachable (model repo versioning, 8.18), use K8s rolling updates with readiness gates,
and automate rollback on SLO burn / regression alerts. Prefer immutable, versioned
artifacts so rollback is deterministic. Practice rollback (game days). "Deploy" isn't
done until "undeploy" is proven.

Chain → Rather than manual rollback loops, how do we automate the whole lifecycle? (9.10)
Verse 9.10 — Automated retraining triggers
Objective 9.4

Close the loop: when drift (9.06), regression (9.07), or quality-metric decline crosses
a threshold, trigger retraining/fine-tuning on fresh data, re-evaluate, and (if it
passes gates) promote via canary. Triggers can be scheduled, metric-based, or
data-volume-based. Guard against feedback loops (training on the model's own biased
outputs). This is MLOps continuous training (CT).

Chain → Retraining and tuning need to be systematic — how? (9.11)
Verse 9.11 — Automated tuning pipelines
Objective 9.4

Wrap retraining in a reproducible pipeline: data validation → (re)train/fine-tune →
automated eval (Domain 6) → gated promotion → canary → monitor. Orchestrate with MLOps
tools; on NVIDIA, NeMo recipes + Base Command / cluster schedulers run the
training jobs, and the eval/serving stack gates promotion. Hyperparameter search (4.34)
can run inside the pipeline. Everything versioned for reproducibility.

Chain → Pipelines produce many models — how do we track them? (9.12)
Verse 9.12 — Model registry, versioning & lineage
Objective 9.4

A model registry tracks every model version with its lineage: training data
snapshot, code/commit, hyperparameters, eval results, and stage (staging/production/
archived). Enables reproducibility, auditability, and one-click rollback. Distinct from
the serving version policy (8.18): the registry is the source of truth; the model repo
is what's deployed. Tag artifacts immutably.

Chain → All this exists to keep the service trustworthy and up — how do we frame that? (9.13)
Verse 9.13 — Uptime, HA & graceful degradation
Objective 9.5

Continuous availability: redundant replicas across nodes/zones, health probes + load
balancing, autoscaling (8.15), and graceful degradation (fall back to a smaller/
cached model, shed load, or return a safe default rather than fail hard). Timeouts,
retries with backoff, and circuit breakers contain failures. Zero-downtime deploys via
rolling updates + rollback (9.09). Reliability is a feature.

Chain → Uptime keeps it running; what keeps users *trusting* it? (9.14)
Verse 9.14 — Transparency, trust & audit trails
Objective 9.5

Trust requires transparency: audit logs of prompts/responses/decisions (privacy-
respecting), model cards documenting capabilities/limitations/intended use,
provenance/lineage (9.12), citations for grounded answers (RAG), and clear user-facing
uncertainty/refusals. Enables incident forensics, compliance, and user confidence — the
bridge into Safety, Ethics & Compliance (Domain 10).

Chain → Transparency and trust lead directly into responsible AI — **Domain 10: Safety, Ethics & Compliance.**
