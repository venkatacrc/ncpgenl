The 18 Verses

Verse 8.01 — Cost profiles: encoder vs decoder vs enc-dec
Objective 8.1
  • Encoder-only: one forward pass, no autoregression, no KV cache — cheapest,
    lowest latency (classification/embeddings).
  • Decoder-only: autoregressive — prefill (parallel) then per-token decode (serial) +
    KV cache; latency scales with output length.
  • Encoder-decoder: full encoder pass + autoregressive decoder + cross-attention —
    most expensive per request, but the encoder runs once.

Match model type to the latency/throughput/cost budget (ties to 1.05–1.07).

Chain → For decoders, generation has two distinct phases — what are they? (8.02)
Verse 8.02 — Prefill vs decode (TTFT, TPOT)
Objective 8.1
  • Prefill: process the whole prompt in parallel, build the KV cache → determines
    TTFT (Time To First Token). Compute-bound (big GEMM over all prompt tokens).
  • Decode: generate one token at a time, each reusing the KV cache → determines
    TPOT (Time Per Output Token) / inter-token latency. Memory-bandwidth-bound
    (loading weights per token at small batch).

End-to-end latency ≈ TTFT + (output_len − 1) × TPOT. Optimizations differ per phase
(7.24).

Chain → These phases pull latency and throughput in opposite directions — how do we balance them? (8.03)
Verse 8.03 — Latency vs throughput tradeoff
Objective 8.1

Larger batches raise throughput (amortize weight loading over more sequences, better
Tensor Core use) but raise per-request latency (queuing + bigger steps). Since decode
is memory-bandwidth-bound, batching many sequences is nearly free on compute up to a
point — the key insight enabling continuous batching (8.08). Pick an operating point on
the latency-throughput curve per SLA; measure with percentiles (6.12).

Chain → To serve this at scale we containerize — what does that pipeline look like? (8.04)
Verse 8.04 — Containerized inference pipeline
Objective 8.2

Package the model + runtime + dependencies into a container for reproducible, portable
deployment. A serving pipeline = preprocess (tokenize) → model (engine) → postprocess
(detokenize), often as a Triton ensemble (8.12). Containers pin CUDA/driver-
compatible runtimes and enable both docker run and Kubernetes deployment. NVIDIA ships
prebuilt serving containers on NGC.

Chain → Where do the model artifacts and container images come from? (8.05)
Verse 8.05 — NGC images & model artifacts
Objective 8.2

NGC (NVIDIA GPU Cloud) is the catalog of GPU-optimized container images (PyTorch,
Triton/Dynamo-Triton, TensorRT-LLM, NeMo), pretrained models, and Helm charts. Pull with
docker pull nvcr.io/nvidia/.... Model artifacts (engines, checkpoints, config.pbtxt)
live in a model repository the server mounts. Pin image tags for reproducibility;
engines are GPU-arch-specific (4.23).

Chain → With container and artifacts, which server serves LLMs and how is it structured? (8.06)
Verse 8.06 — Dynamo-Triton architecture & model repo
Objective 8.2

Dynamo-Triton (formerly Triton Inference Server) serves models across
backends (TensorRT-LLM, vLLM, PyTorch, ONNX, Python) behind HTTP/gRPC. A model
repository holds one directory per model with versioned weights/engines and a
config.pbtxt declaring inputs/outputs, backend, batching, and instance groups.
Features: dynamic/continuous batching, concurrent execution, ensembles, metrics
endpoint.

Chain → How does Triton batch incoming requests to raise throughput? (8.07)
Verse 8.07 — Dynamic batching
Objective 8.2

Triton's dynamic batcher holds incoming requests briefly (up to
max_queue_delay_microseconds) to combine them into a larger batch before running the
model — raising throughput/GPU utilization. It batches at the request level and waits
for the batch to finish together. Great for fixed-size/non-autoregressive models
(encoders). For autoregressive LLMs with variable output lengths it's suboptimal (short
requests wait for long ones) — hence continuous batching (8.08).

Chain → Why is dynamic batching not ideal for autoregressive generation? (8.08)
Verse 8.08 — Continuous (in-flight) batching
Objective 8.2

Continuous / in-flight batching (TensorRT-LLM) operates at the iteration
(token-step) level: as soon as one sequence in the batch finishes, its slot is freed
and a queued request joins immediately — no waiting for the whole batch. This keeps the
GPU saturated despite highly variable output lengths, dramatically improving throughput
and latency for LLM serving. Paired with paged KV cache for memory efficiency.

Chain → So when do I use dynamic vs continuous batching? (8.09)
Verse 8.09 — Dynamic vs continuous batching decision
Objective 8.2
Dynamic batching Continuous (in-flight) batching
Granularity request level token/iteration level
Waits for batch to finish together nothing — slot freed per finished seq
Best for fixed-size / encoders / non-AR autoregressive LLM generation
Backend generic Triton TensorRT-LLM / vLLM

Rule: LLM text generation → continuous batching. Fixed-shape models (embeddings,
classifiers) → dynamic batching.

Chain → Some models carry state across requests — how are those batched? (8.10)
Verse 8.10 — Sequence batcher (stateful models)
Objective 8.2

Triton's sequence batcher routes all requests of a correlation ID (a session/
stream) to the same model instance in order, preserving per-sequence state across
calls — what the dynamic batcher does not do. Used for stateful/streaming models
(session-based RNNs, stateful decoding, conversational state held server-side). Manages
sequence start/end/ready control signals.

Chain → Batching aside, how do we run multiple models/instances at once on a GPU? (8.11)
Verse 8.11 — Concurrent execution & instance groups
Objective 8.2

instance_group in config.pbtxt sets how many instances of a model run and on
which GPUs, enabling concurrent model execution — multiple models or multiple copies
of one model serving in parallel to fill the GPU and hide per-request latency. More
instances → higher throughput until memory/compute saturate. Combine with dynamic/
continuous batching.

instance_group [ { count: 2, kind: KIND_GPU, gpus: [0] } ]
Chain → Real pipelines chain preprocess/model/postprocess — how are those composed? (8.12)
Verse 8.12 — Ensemble / BLS workflows
Objective 8.2
  • Ensemble: a config.pbtxt DAG wiring models together (tokenizer → model →
    detokenizer) so the server runs the whole pipeline in one request, avoiding
    client round-trips.
  • BLS (Business Logic Scripting): a Python backend model that calls other models
    with control flow (loops, conditionals) — for dynamic pipelines (e.g. RAG:
    embed → retrieve → generate) that a static ensemble DAG can't express.
Chain → Beyond raw Triton, NVIDIA packages models as microservices — what are those? (8.13)
Verse 8.13 — NIM microservices overview
Objective 8.2

NVIDIA NIM (NVIDIA Inference Microservices) package an optimized model (often
TensorRT-LLM engine) + Triton + an OpenAI-compatible REST API into a single
container with sensible defaults, auto-selecting the best engine for the detected GPU.
NIM trades some low-level control for turnkey, production-grade deployment and standard
APIs. Part of NVIDIA AI Enterprise.

Chain → When do I reach for a NIM vs configuring raw Triton myself? (8.14)
Verse 8.14 — NIM vs raw Triton decision
Objective 8.2
NIM Raw Dynamo-Triton
Setup turnkey, OpenAI-compatible API manual model repo + config.pbtxt
Optimization auto-selects engine per GPU you build/tune engines
Control opinionated defaults full control (backends, ensembles, BLS)
Best for standard LLMs, fast time-to-prod custom pipelines, non-standard models

Rule: NIM for supported models and speed; raw Triton for custom ensembles, unusual
backends, or fine-grained control.

Chain → However we package it, how do we scale/orchestrate it in production? (8.15)
Verse 8.15 — Kubernetes serving (HPA, readiness)
Objective 8.3

Deploy the serving container as a K8s Deployment with GPU resource requests,
readiness/liveness probes (Triton's /v2/health/ready) so traffic only routes to
ready pods, and a Service/ingress. Scale with the Horizontal Pod Autoscaler
(HPA) on GPU/custom metrics (queue depth, latency). NVIDIA provides Helm charts and the
GPU Operator. Use rolling updates for zero-downtime (ties to 9.13).

Chain → Not everyone runs K8s — what's the minimal bare path? (8.16)
Verse 8.16 — `docker run` serving path
Objective 8.3

Minimal single-node serving without orchestration:

docker run --gpus all --rm -p 8000:8000 -p 8001:8001 -p 8002:8002 \
  -v "$PWD/model_repo":/models \
  nvcr.io/nvidia/tritonserver:24.07-py3 \
  tritonserver --model-repository=/models

Ports: 8000 HTTP, 8001 gRPC, 8002 Prometheus metrics (9.01). Query with the client
SDK or curl. This is the reproducible baseline every lab mirrors; K8s (8.15) wraps the
same container.

Chain → Once serving, how do we watch it live? (8.17)
Verse 8.17 — Live monitoring (Triton metrics endpoint)
Objective 8.3

Dynamo-Triton exposes Prometheus metrics on port 8002: inference count, request/
queue/compute latencies, batch sizes, GPU utilization/memory, and (for TRT-LLM)
LLM-specific counters. Scrape with Prometheus, visualize in Grafana. This is the bridge
into Production Monitoring (Domain 9). Instrument from day one, not after an incident.

Chain → Serving evolves — how do we manage model versions safely? (8.18)
Verse 8.18 — Model versioning & config.pbtxt
Objective 8.3

The model repository is versioned: numbered subdirectories (1/, 2/) under each
model; config.pbtxt's version policy controls which serve (latest, specific, all).
This enables safe rollout/rollback and A/B or canary (9.08–9.09) by serving multiple
versions simultaneously. config.pbtxt also pins backend, batching, instance groups,
and I/O — the single source of truth for a served model.

version_policy { specific { versions: [2] } }
