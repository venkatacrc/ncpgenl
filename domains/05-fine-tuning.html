The 26 Verses

Verse 5.01 — SFT: full fine-tuning
Objective 5.1

Supervised fine-tuning (SFT) continues training a pretrained model on labeled
(prompt, completion) pairs, updating all weights via the CLM loss (2.15) masked to
the completion (2.16). Full FT gives maximum capacity to adapt but costs
memory = params + gradients + optimizer states (Adam ≈ 2× params) + activations — often
prohibitive for large models (motivating PEFT, 5.10). Risk: catastrophic forgetting
(5.26).

Chain → Raw SFT teaches tasks; how do we specifically make a model follow chat instructions? (5.02)
Verse 5.02 — Instruction tuning & chat format
Objective 5.1

Instruction tuning is SFT on diverse (instruction, response) data rendered in the chat
template (2.01, 3.10), teaching the model to follow instructions and hold multi-turn
conversations. Loss is masked to assistant turns only. Quality/diversity of
instructions matters more than sheer volume. This produces the "instruct"/"chat"
variant from a base model.

Chain → Instruction-tuned models still may not match human *preferences* — how do we align to those? (5.03)
Verse 5.03 — RLHF pipeline (SFT → RM → PPO)
Objective 5.1

Reinforcement Learning from Human Feedback aligns models to preferences in three
stages: (1) SFT base; (2) train a reward model (5.04) on human preference
comparisons; (3) RL-optimize the policy against the reward model with PPO
(5.05), regularized by a KL penalty to the SFT reference. Powerful but complex: four
models in memory (policy, reference, reward, value), unstable, expensive.

Chain → The pipeline depends on a reward model — how is it trained? (5.04)
Verse 5.04 — Reward modeling (preference pairs)
Objective 5.1

A reward model (RM) scores a response's quality. Trained on human preference pairs
(prompt, chosen, rejected) with the Bradley-Terry loss:

$$\mathcal{L}_{RM}=-\log\sigma\big(r_\theta(x,y_{chosen})-r_\theta(x,y_{rejected})\big)$$

The RM is usually the SFT model with a scalar head. It provides the reward signal PPO
optimizes. Quality/coverage of preference data caps final alignment quality.

Chain → With a reward model, how does PPO update the policy without destroying it? (5.05)
Verse 5.05 — PPO in RLHF (policy/value, KL penalty)
Objective 5.1

Proximal Policy Optimization treats generation as RL: the policy (LLM) generates,
the reward model scores, a value network estimates baselines, and a clipped
surrogate objective bounds each update. A KL penalty to the frozen SFT reference
keeps the policy from drifting into reward-hacking gibberish:

$$\text{reward} = r_\theta(x,y) - \beta\,\text{KL}\big(\pi_\theta \,\|\, \pi_{ref}\big)$$

Sensitive to hyperparameters; the value net doubles memory. This complexity motivates
DPO.

Chain → PPO needs a reward model and RL machinery — can we align directly from preferences instead? (5.06)
Verse 5.06 — DPO: direct preference optimization
Objective 5.1

DPO skips the explicit reward model and RL loop: it reparameterizes the RLHF objective
so the optimal policy defines an implicit reward, giving a simple classification
loss on preference pairs against a frozen reference:

$$\mathcal{L}_{DPO}=-\log\sigma\!\Big(\beta\log\frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)}-\beta\log\frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}\Big)$$

(y_w=chosen, y_l=rejected). Only policy + reference in memory; stable, no reward
model, no sampling loop. The β controls deviation from the reference.

Chain → DPO is simpler than PPO — when would I still prefer one over the other? (5.07)
Verse 5.07 — DPO vs RLHF/PPO tradeoffs
Objective 5.1
  • DPO: simpler, stable, cheaper (no RM/value net, no online sampling), needs a fixed
    preference dataset. Can overfit to the dataset and is off-policy.
  • PPO/RLHF: on-policy exploration via a reward model can exceed the static dataset
    and optimize non-differentiable/complex rewards, but is unstable, memory-heavy, and
    hard to tune.

Rule: default to DPO for preference alignment; use PPO when you need online
exploration, a learned reward covering many behaviors, or reward signals you can't bake
into pairs.

Chain → Both DPO and PPO have limits — what newer method drops the value network for reasoning RL? (5.08)
Verse 5.08 — GRPO: group relative policy optimization
Objective 5.1

GRPO (from DeepSeek-R1-style reasoning training) removes PPO's value network:
for each prompt it samples a group of G responses, scores them (often with a
verifiable/rule-based reward), and uses the group mean/std as the baseline so the
advantage is each response's reward normalized within its group:

$$A_i=\frac{r_i-\text{mean}(r_{1..G})}{\text{std}(r_{1..G})}$$

Cheaper than PPO (no value net), well-suited to reasoning tasks with automatic reward
checking.

Chain → With PPO, DPO, and GRPO on the table, how do I choose? (5.09)
Verse 5.09 — GRPO vs PPO vs DPO decision
Objective 5.1
Method Reward model? Value net? Data Best for
DPO no (implicit) no fixed preference pairs cheap, stable preference alignment
PPO yes (learned) yes online rollouts rich/complex rewards, exploration
GRPO reward fn (often rule-based) no grouped rollouts reasoning/verifiable rewards, cheaper RL

Escalate DPO → GRPO → PPO as reward complexity and need for online exploration rise.

Chain → Alignment methods update behavior; but most of us can't afford full FT — how do we adapt parameter-efficiently? (5.10)
Verse 5.10 — LoRA: low-rank decomposition math
Objective 5.2

LoRA freezes pretrained W₀ ∈ ℝ^{d×k} and learns a low-rank update:

$$W = W_0 + \Delta W = W_0 + \frac{\alpha}{r} BA,\qquad B\in\mathbb{R}^{d\times r},\; A\in\mathbb{R}^{r\times k},\; r\ll\min(d,k)$$

Only A, B train (parameters ∝ r(d+k) instead of d·k). A init random Gaussian,
B init zero (so ΔW starts at 0). At inference BA can be merged into W₀ → zero
added latency.

delta = (alpha / r) * (B @ A)   # add to W0
Chain → LoRA has knobs — which matter and how are they set? (5.11)
Verse 5.11 — LoRA hyperparameters
Objective 5.2
  • rank r: capacity of the update (4–64 typical); too low underfits, too high wastes
    params and risks overfit.
  • alpha α: scaling; effective scale α/r. Common heuristic α = 2r.
  • target modules: which projections get adapters — attention q_proj,k_proj,v_proj, o_proj (and often MLP). More targets = more capacity.
  • dropout: regularizes the adapter.
from peft import LoraConfig
cfg = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,
                 target_modules=["q_proj","k_proj","v_proj","o_proj"])
Chain → LoRA still loads the base in FP16 — how do we fine-tune when even that won't fit? (5.12)
Verse 5.12 — QLoRA (4-bit base + LoRA)
Objective 5.2

QLoRA quantizes the frozen base to 4-bit (NF4, a normal-float format optimal for
normally-distributed weights), then trains LoRA adapters in BF16 on top. Adds
double quantization (quantize the quantization constants) and paged optimizers
(offload optimizer states to CPU on memory spikes). Result: fine-tune a 65B model on a
single 48 GB GPU. Base stays 4-bit; gradients flow only into the BF16 adapters.

Chain → One base can host many adapters — how do we serve them together? (5.13)
Verse 5.13 — Multi-LoRA serving
Objective 5.2

Because adapters are tiny and the base is shared, one deployment can serve many LoRA
adapters simultaneously, routing each request to its adapter (per-task/per-tenant).
The base weights load once; adapters swap cheaply (or batch heterogeneously with
specialized kernels). NVIDIA supports multi-LoRA in TensorRT-LLM / NIM. Trade-off:
un-merged adapters add a small per-layer compute overhead vs a merged single-task model.

Chain → LoRA is one PEFT family — what are the alternatives? (5.14)
Verse 5.14 — Adapters (bottleneck modules)
Objective 5.2

Adapter tuning inserts small bottleneck modules (down-project → nonlinearity →
up-project, with a residual) between frozen transformer sublayers; only adapters
train. Unlike LoRA (which reparameterizes existing weight matrices and can be merged),
adapters add new layers, so they cannot be merged away and add inference latency.
Historically first PEFT method; LoRA largely superseded it for LLMs.

Chain → LoRA/adapters modify weights or add layers — is there a PEFT that only touches the input? (5.15)
Verse 5.15 — P-tuning / prefix tuning (continuous prompts)
Objective 5.2

Prompt tuning / P-tuning prepend trainable continuous embedding vectors (soft
prompts, 2.12) to the input; the model and all real weights stay frozen — only the
prompt vectors train. Prefix tuning goes further: it prepends trainable vectors to
the keys/values at every layer, not just the input embedding, giving more capacity.
Extremely parameter-efficient (thousands of params), but usually less expressive than
LoRA for hard tasks.

Chain → There are two P-tuning variants — how do they differ? (5.16)
Verse 5.16 — P-tuning v2 vs prompt tuning
Objective 5.2
  • Prompt tuning / P-tuning (v1): soft prompts only at the input layer. Works
    well only at large scale; weak on smaller models and hard sequence-labeling tasks.
  • P-tuning v2: adds tunable prompts at every layer (deep prompt tuning, akin to
    prefix tuning), matching full fine-tuning across scales and tasks.

NeMo implements P-tuning; the exam may contrast "prompt tuning" (shallow) vs "P-tuning
v2 / prefix" (deep).

Chain → With four PEFT families known, how do I choose among them and full FT? (5.17)
Verse 5.17 — PEFT decision: LoRA vs adapters vs P-tuning vs full FT
Objective 5.2
Method Trains Merge-able? Inference cost Capacity
Full FT all weights n/a none extra highest (+ forgetting risk)
LoRA/QLoRA low-rank ΔW yes zero if merged high
Adapters bottleneck layers no small latency medium
P-tuning/prefix soft prompt vecs no tiny low–medium

Rule: LoRA/QLoRA is the default (mergeable, strong, cheap). Full FT only with ample
data/compute and forgetting mitigation. P-tuning for extreme parameter efficiency /
many tasks. Adapters mostly legacy.

Chain → PEFT covers task adaptation; a distinct fine-tuning goal is *embeddings* — how are those trained? (5.18)
Verse 5.18 — Contrastive loss for embeddings
Objective 5.2

Embedding models are fine-tuned so similar texts are close and dissimilar far apart.
- Triplet loss: max(0, d(a,p) − d(a,n) + margin) — anchor closer to positive than
negative by a margin.
- InfoNCE / contrastive: treat the matching pair as positive against in-batch
negatives:

$$\mathcal{L}=-\log\frac{\exp(\text{sim}(a,p)/\tau)}{\sum_i \exp(\text{sim}(a,n_i)/\tau)}$$

Temperature τ sharpens; large in-batch negatives help. Basis of retrieval/RAG
embedding quality (2.24, 6.08).

Chain → Contrastive training produces embeddings — what's the standard model shape? (5.19)
Verse 5.19 — Sentence-embedding fine-tuning (bi-encoder)
Objective 5.2

A bi-encoder encodes query and document separately into vectors compared by
cosine — fast, precomputable, the backbone of retrieval/RAG. Contrast the
cross-encoder, which jointly encodes a (query, doc) pair for a relevance score —
more accurate but O(n) per query, used for re-ranking the bi-encoder's top-k.
Fine-tune bi-encoders with contrastive loss (5.18) on (query, positive, negatives).
NVIDIA: NeMo Retriever embedding + reranking models.

Chain → Fine-tuning risks overfitting — how do we stop training at the right time? (5.20)
Verse 5.20 — Early stopping & patience
Objective 5.3

Monitor a validation metric each eval interval; stop when it fails to improve for
patience consecutive checks, and restore the best checkpoint. Prevents overfitting
and wasted compute. Levers: patience, min_delta (minimum improvement to count),
which metric to watch. Pairs with a warmup/cosine schedule (4.32) and HP search
(4.34, kill weak trials early).

if val_metric < best - min_delta:
    best, wait = val_metric, 0; save("best.pt")
else:
    wait += 1
    if wait >= patience: stop()
Chain → Early stopping fights overfitting — what other signals reveal it? (5.21)
Verse 5.21 — Overfitting signals & regularization
Objective 5.3

Signal: training loss keeps falling while validation loss rises (diverging curves).
Regularizers: weight decay (L2), dropout, data augmentation, smaller
LoRA rank, fewer epochs, and more/diverse data. For LLM fine-tuning, 1–3 epochs on
instruction data is often enough; more epochs memorize. Label smoothing softens
over-confidence.

Chain → Detecting overfitting requires the right metric — which per phase? (5.22)
Verse 5.22 — Metric selection per phase
Objective 5.3

Match the metric to the phase and task:
- Training: loss (CLM/contrastive) for optimization.
- Validation: task metric for model selection/early stopping — perplexity (LM),
accuracy/F1 (classification), BLEU/ROUGE (generation), retrieval recall@k
(embeddings).
- Test: held-out final report; add human/LLM-judge for open-ended quality (Domain
6).

Never select the model on the test set (leakage, 3.11). Pick a single primary
metric to avoid ambiguous model selection.

Chain → Metrics assess quality; a specific failure to fix in fine-tuning is hallucination — how? (5.23)
Verse 5.23 — Hallucination mitigation via fine-tuning
Objective 5.4

Fine-tuning levers against hallucination: train on high-quality grounded data
(answers tied to sources), include "I don't know" examples so refusal is learned,
prefer RAG for knowledge-heavy tasks over parametric memorization (2.21, 2.23), and
align with preference methods (DPO) that penalize fabrication. Over-training on narrow
data can increase confident hallucination — balance with diverse data.

Chain → Fine-tuning reduces hallucination probabilistically — what enforces it at runtime? (5.24)
Verse 5.24 — NeMo Guardrails for hallucination control (xref D10)
Objective 5.4

Runtime enforcement complements fine-tuning: NeMo Guardrails can add a
fact-checking / self-check output rail that verifies a response against retrieved
sources (or a second LLM call) and blocks/《revises unsupported claims. The guide cites
integrating Cleanlab Trustworthy Language Model in NeMo Guardrails for
hallucination scoring. Fine-tuning lowers the rate; guardrails catch the residue. Full
guardrails treatment in 10.09–10.10.

Chain → After mitigation, how do we quantify whether fine-tuning actually helped? (5.25)
Verse 5.25 — Assessing fine-tuning impact (xref D6)
Objective 5.4

Measure before/after on a held-out set with the primary task metric and a
regression check on general capability (to catch forgetting, 5.26). Use paired
comparisons, fixed decoding/seeds, and enough samples for significance. Track both the
target improvement and side-effects (safety, other tasks). Formal evaluation frameworks
(Ragas, NeMo Evaluator, LLM-as-judge) are Domain 6.

Chain → A key risk when assessing impact is losing prior abilities — what is it and how to prevent it? (5.26)
Verse 5.26 — Catastrophic forgetting & mitigation
Objective 5.4

Fine-tuning on a narrow task can overwrite general capabilities — catastrophic
forgetting. Mitigations: PEFT (LoRA freezes the base, structurally limiting drift),
lower LR / fewer epochs, replay (mix in general/pretraining data), regularization
toward the base (EWC, KL to reference — the same mechanism as RLHF's KL penalty, 5.05),
and multi-task instead of sequential training. PEFT's inherent resistance to forgetting
is a key reason it's the default.
