The 28 Verses

Verse 7.01 — Parallelism taxonomy
Objective 7.1

Ways to split a training job across GPUs: data parallel (replicate model, split
batch — DDP/FSDP), tensor parallel (split individual layers' matrices),
pipeline parallel (split layers into stages), sequence parallel (split the
sequence dimension), expert parallel (split MoE experts). They compose into 3D/4D
parallelism. Choose based on whether the bottleneck is throughput (data) or model size
(model/tensor/pipeline).

Chain → Start with the simplest: how does data parallelism sync gradients? (7.02)
Verse 7.02 — DDP: gradient all-reduce
Objective 7.1

Distributed Data Parallel replicates the full model on each GPU, each processes a
different micro-batch, then all-reduce averages gradients across ranks (NCCL
ring all-reduce — bandwidth-optimal). Overlaps gradient communication with the
backward pass (gradient bucketing). Requires the whole model + optimizer to fit on one
GPU. Near-linear scaling until communication dominates.

import torch.distributed as dist
model = torch.nn.parallel.DistributedDataParallel(model, device_ids=[local_rank])
# gradients all-reduced automatically during backward()
Chain → DDP needs the whole model per GPU — what if it doesn't fit? (7.03)
Verse 7.03 — FSDP / ZeRO stages
Objective 7.1

Fully Sharded Data Parallel (≈ DeepSpeed ZeRO) shards what DDP replicates:
- ZeRO-1: shard optimizer states.
- ZeRO-2: + shard gradients.
- ZeRO-3 / FSDP: + shard parameters — each GPU holds a slice, all-gathers the
full layer just-in-time for forward/backward, then frees it.

Trades extra communication for a large memory reduction, fitting models far bigger than
one GPU while keeping the data-parallel programming model.

Chain → Sharding data-parallel still replicates compute per layer — how do we split a single layer's math? (7.04)
Verse 7.04 — Tensor parallelism (Megatron)
Objective 7.1

Tensor Parallelism (TP) splits individual weight matrices across GPUs (intra-layer).
Megatron splits attention/MLP GEMMs column- then row-wise so each GPU computes a shard
and an all-reduce combines partial results per layer. High communication volume →
keep TP within the NVLink domain; don't span slow inter-node links. Enables layers
too big for one GPU.

GB200/NVL72 note: "within a node" traditionally meant ~8 GPUs (NVLink+NVSwitch).
A GB200 NVL72 rack is a single 72-GPU NVLink domain, so TP (and EP, 7.07) can
scale to far more GPUs at NVLink bandwidth than the 8-GPU rule assumes — reshaping the
TP×PP×DP mapping (7.09).

Chain → TP splits within a layer; how do we split *across* layers? (7.05)
Verse 7.05 — Pipeline parallelism (micro-batches, bubble)
Objective 7.1

Pipeline Parallelism (PP) splits the model into stages of consecutive layers on
different GPUs; activations pass stage→stage. A naive pipeline idles most GPUs (the
bubble). Splitting the batch into micro-batches (GPipe / interleaved 1F1B
schedules) keeps stages busy and shrinks the bubble. Bubble fraction ≈ (p−1)/(m+p−1)
for p stages, m micro-batches — more micro-batches → smaller bubble. Low comm volume
(only stage boundaries) → can span nodes.

Chain → Attention activations grow with sequence length — how do we parallelize that dimension? (7.06)
Verse 7.06 — Sequence parallelism
Objective 7.1

Sequence Parallelism (SP) splits along the sequence/token dimension, sharding the
activations of the normally-replicated ops (LayerNorm, dropout) that Tensor Parallelism
leaves un-split. Combined with TP (Megatron-SP), it cuts activation memory for long
sequences without extra compute. For very long context, context/ring-attention variants
extend this idea across GPUs.

Chain → Some models have many experts, not one FFN — how do we parallelize those? (7.07)
Verse 7.07 — Expert parallelism (MoE)
Objective 7.1

Mixture-of-Experts replaces the FFN with many experts; a router sends each token to
top-k experts (sparse activation → more params, ~constant FLOPs/token). Expert
Parallelism (EP) places different experts on different GPUs; an all-to-all shuffles
tokens to their expert's GPU and back. Challenge: load balancing (add an auxiliary
balancing loss) so no expert is a bottleneck.

Chain → With all these axes, how do I decide which to use? (7.08)
Verse 7.08 — Data vs model parallel decision
Objective 7.1
  • Fits on one GPU, want speed → Data Parallel (DDP).
  • Optimizer/grad memory too big → FSDP/ZeRO (still data-parallel model).
  • A single layer too big → Tensor Parallel (keep within a node/NVLink).
  • Whole model too big for a node → Pipeline Parallel across nodes.
  • Long sequences → Sequence Parallel (+ TP).
  • MoE → Expert Parallel.

Order of preference by comm cost: DP/FSDP ≤ PP (low comm, cross-node) < TP (high comm,
intra-node) < EP (all-to-all).

Chain → Real large-scale training combines these — how? (7.09)
Verse 7.09 — 3D parallelism composition
Objective 7.1

Large LLM training composes TP × PP × DP (often + SP, + EP): e.g. TP=8 within a
node (NVLink), PP across nodes, DP across the remaining replicas. Total GPUs =
TP·PP·DP. Place high-communication TP on the fastest interconnect, PP on slower links,
DP outermost. NeMo/Megatron-Core expose these as config knobs. Getting the mapping right
to the topology is the difference between linear and terrible scaling.

GB200/NVL72: with a 72-GPU NVLink domain (7.04) you can set a much larger TP (and
EP) that still stays on NVLink, shrinking cross-node PP/DP traffic — retune the mapping
to the bigger domain rather than defaulting to TP=8.

Chain → Parallelism spreads work; how do we speed up the math on each GPU? (7.10)
Verse 7.10 — Mixed precision (AMP) & loss scaling
Objective 7.2

Automatic Mixed Precision runs most ops in FP16/BF16 (fast Tensor Cores, half memory)
while keeping a master FP32 copy of weights and FP32 accumulations for stability. FP16
needs loss scaling: multiply the loss before backward so small gradients don't
underflow to zero, then unscale before the optimizer step (dynamic scaler adjusts the
factor). BF16 needs no loss scaling (FP32 exponent range, 4.07).

scaler = torch.cuda.amp.GradScaler()
with torch.autocast("cuda", dtype=torch.float16):
    loss = model(x).loss
scaler.scale(loss).backward(); scaler.step(opt); scaler.update()
Chain → Mixed precision feeds Tensor Cores — how do we make sure they're actually used? (7.11)
Verse 7.11 — Tensor Core utilization (dim alignment)
Objective 7.2

Tensor Cores accelerate matmuls only when dimensions align to their tile sizes:
GEMM dims (batch, hidden, vocab) should be multiples of 8 (FP16) or 16 (INT8),
and larger multiples (64/128) help. Misaligned dims (e.g. vocab 50257, odd hidden) fall
back to slower paths or waste cycles on padding. Pad vocab/hidden to friendly multiples.
Verify with Nsight Compute (7.22) that Tensor Core (HMMA/IMMA) pipes are active.

Chain → FP16 vs BF16 both use Tensor Cores — which for training stability? (7.12)
Verse 7.12 — BF16 vs FP16 training stability
Objective 7.2

Both are 16-bit Tensor Core formats. BF16 (1-8-7) has FP32's exponent range → no
loss scaling, robust to overflow, the default for LLM pretraining on Ampere+.
FP16 (1-5-10) has more mantissa precision but a narrow range → needs loss scaling
and can still overflow on large activations/gradients. Rule: prefer BF16 for training
stability; use FP16 only where required.

Chain → On H100 there's an 8-bit training path — what is it? (7.13)
Verse 7.13 — Transformer Engine FP8 recipes `[H100-ONLY]`
Objective 7.2

Transformer Engine (TE) provides FP8 training/inference on Hopper+: FP8 GEMMs
(E4M3 fwd, E5M2 grads, 4.06) with per-tensor scaling factors maintained via a
delayed-scaling recipe (track a rolling window of amax to set scales). Wrap layers
in te.Linear/te.TransformerLayer under an fp8_autocast. Big speedup + memory cut on
H100 with near-BF16 accuracy.

GB200/Blackwell upgrade: the 2nd-gen Transformer Engine (sm_100) adds FP4
(NVFP4) training/inference with micro-block scaling (4.08) — finer-grained than
Hopper's per-tensor delayed scaling — for even higher throughput and smaller memory.
A100 fallback: use BF16 AMP (7.10/7.12) — same mixed-precision concept, no FP8/FP4
units on Ampere.

import transformer_engine.pytorch as te
from transformer_engine.common.recipe import DelayedScaling
with te.fp8_autocast(enabled=True, fp8_recipe=DelayedScaling()):
    out = te_model(x)
Chain → Precision aside, what dominates memory and how do we manage it? (7.14)
Verse 7.14 — Batch / memory management (activations)
Objective 7.2

Training memory = weights + gradients + optimizer states + activations. Activation
memory scales with batch × sequence × hidden × layers and often dominates at long
context. Levers: reduce micro-batch (+ gradient accumulation, 7.15), gradient/activation
checkpointing (7.16), sequence parallelism (7.06), and lower precision. Increasing batch
raises throughput and activation memory together — tune to fill the GPU without OOM.

Chain → If we need a big effective batch but memory is tight, how? (7.15)
Verse 7.15 — Gradient accumulation (effective batch)
Objective 7.3

Accumulate gradients over k micro-batches before an optimizer step to simulate a
k× larger batch without the memory cost:

effective_batch = micro_batch × k × data_parallel_world_size

Do not zero grads between micro-steps; step + zero after k. Divide loss by k so
the gradient magnitude matches a true large batch. Trades more forward/backward passes
per update for memory headroom (pairs with the linear scaling rule, 4.33).

for i, batch in enumerate(loader):
    loss = model(**batch).loss / k
    loss.backward()
    if (i + 1) % k == 0:
        opt.step(); opt.zero_grad()
Chain → Accumulation stores activations per micro-batch — how do we cut *that* memory? (7.16)
Verse 7.16 — Gradient (activation) checkpointing
Objective 7.3

Instead of storing every layer's activations for the backward pass, store only a few
checkpoints and recompute the rest during backward. Cuts activation memory from
O(L) toward O(√L) at the cost of ~1 extra forward (~30% more compute). Enables larger
batches/models on limited memory — the standard OOM remedy alongside gradient
accumulation.

from torch.utils.checkpoint import checkpoint
out = checkpoint(layer, x)   # recompute activations in backward
Chain → Memory managed; the attention GEMM is the hot compute — how is it optimized? (7.17)
Verse 7.17 — Attention GEMM & FlashAttention
Objective 7.3

Naive attention materializes the T×T score matrix in HBM → memory-bandwidth-bound and
O(T²) memory. FlashAttention fuses the softmax·(QKᵀ)·V into one kernel using
tiling + online softmax, keeping intermediates in SRAM and never writing the full
matrix — O(T) memory, far higher throughput, IO-aware. It's the reason long context is
feasible. NVIDIA ships fused attention via cuDNN / Transformer Engine.

Chain → With tensor parallelism, how is the multi-head attention GEMM split across GPUs? (7.18)
Verse 7.18 — MHA GEMM distribution across TP
Objective 7.3

In Megatron tensor parallelism, attention is split by heads: each GPU owns a subset
of heads and computes their QKV projections and attention independently (column-parallel
QKV), then the output projection is row-parallel with a single all-reduce to combine.
Because heads are independent (1.03), this splits cleanly with communication only at the
output projection. Keep head count divisible by the TP size.

Chain → Knowing all this, how do we compute whether a model+batch even fits? (7.19)
Verse 7.19 — Training memory formula
Objective 7.2

Approximate GPU memory for training (mixed precision, Adam):
- Weights: P × 2 bytes (BF16).
- Gradients: P × 2 bytes.
- Optimizer (Adam): FP32 master + m + v ≈ P × 12 bytes.
- Activations: ∝ batch × seq × hidden × layers (dominant at long context;
checkpointing cuts it).

Rule of thumb: full Adam training ≈ ~16–20 bytes/param before activations, so a 7B
model needs ~112–140 GB → why FSDP/parallelism/PEFT. Inference adds the KV cache
(4.26) instead of optimizer states.

Chain → When this budget is exceeded, what happens and how do we diagnose it? (7.20)
Verse 7.20 — OOM diagnosis & mitigation
Objective 7.4

CUDA OOM = requested allocation exceeds free VRAM (watch fragmentation too).
Mitigations, cheapest first: reduce micro-batch, gradient accumulation (7.15),
activation checkpointing (7.16), lower precision (BF16/FP8), shorter max_seq_len,
FSDP/ZeRO (7.03), CPU/NVMe offload, PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
for fragmentation. Diagnose with torch.cuda.memory_summary() and the memory snapshot/
profiler.

GB200/Grace-Blackwell: the Grace CPU and Blackwell GPU share coherent, NVLink-C2C
memory, so CPU offload is far cheaper than PCIe offload — large KV cache / optimizer
state can spill to Grace LPDDR with much less penalty, and FP4 weights (4.08) further
cut the footprint.

Chain → OOM is one bottleneck; how do we profile the whole timeline to find others? (7.21)
Verse 7.21 — Nsight Systems (timeline, system-level)
Objective 7.4

Nsight Systems (nsys) is the system-wide timeline profiler: CPU/GPU activity,
CUDA API calls, kernel launches, memcpy, NCCL comm, and gaps. Use it to find coarse
problems: GPU idle bubbles, CPU-bound data loading, poor compute/comm overlap, launch
gaps, host-device sync stalls. Answers "where is time going across the system." Not for
per-kernel internals — that's Nsight Compute.

nsys profile -o report python train.py    # then open in Nsight Systems UI
Chain → Once you find a slow kernel, how do you look *inside* it? (7.22)
Verse 7.22 — Nsight Compute (kernel-level)
Objective 7.4

Nsight Compute (ncu) is the per-kernel profiler: occupancy, memory vs compute
throughput, warp stalls, register/shared-memory usage, Tensor Core (HMMA/IMMA)
utilization, and a roofline chart. Use it after Nsight Systems localizes a hot
kernel, to answer "why is this kernel slow." Division of labor: Systems = timeline/
where; Compute = kernel/why.

ncu --set full -o krep python train.py
Chain → Nsight reports occupancy — what does low occupancy indicate? (7.23)
Verse 7.23 — Kernel underutilization / low occupancy
Objective 7.4

Occupancy = active warps / max warps per SM. Low occupancy or low Tensor Core
utilization signals underutilization, from: too-small batch/dims (not enough parallel
work), register/shared-memory pressure limiting resident warps, memory-bound stalls, or
misaligned dims skipping Tensor Cores (7.11). Fixes: larger batch, kernel fusion, fix
alignment, reduce register spilling. Note: high occupancy is not the goal in itself —
sufficient occupancy to hide latency is.

Chain → Is a slow kernel limited by compute or memory? How do we tell? (7.24)
Verse 7.24 — Compute-bound vs memory-bound (roofline)
Objective 7.4

Arithmetic intensity = FLOPs / bytes moved. The roofline plots achievable
FLOP/s vs intensity: low intensity → memory-bound (limited by HBM bandwidth); high
intensity → compute-bound (limited by peak FLOP/s). LLM decode (batch 1, one
token) is memory-bound (weight loading dominates) → weight-only quant helps (4.04);
prefill/large-batch GEMMs are compute-bound → low-precision compute (FP8/INT8) helps.
Diagnose with Nsight Compute's roofline.

Chain → Multi-GPU adds communication as a bottleneck — how do we spot it? (7.25)
Verse 7.25 — NCCL communication bottlenecks & overlap
Objective 7.4

At scale, collective communication (all-reduce, all-gather, all-to-all) can dominate.
NCCL implements bandwidth-optimal collectives over NVLink/PCIe/InfiniBand. Symptoms
in Nsight Systems: GPUs idle waiting on NCCL. Remedies: overlap comm with compute
(DDP gradient bucketing, FSDP prefetch), place high-comm parallelism (TP) on NVLink
within a node (7.04/7.09), gradient compression, and larger fused buffers. Watch for a
straggler GPU serializing the collective.

Chain → Overlap needs async execution — what primitive enables it? (7.26)
Verse 7.26 — CUDA streams & async overlap
Objective 7.4

A CUDA stream is an ordered queue of GPU work; operations in different streams
can run concurrently. This enables overlapping compute with H2D/D2H copies (use pinned
memory + non_blocking=True) and with NCCL comm. The default stream serializes;
frameworks use multiple streams internally. Missing overlap (everything on one stream,
blocking copies) shows as timeline gaps in Nsight Systems.

Chain → Kernel *launch* overhead can also bottleneck — how do we cut it? (7.27)
Verse 7.27 — torch.compile / CUDA graphs (launch overhead)
Objective 7.4

Many tiny kernels make launch overhead (CPU dispatching each kernel) the
bottleneck — common in decode with small batches. CUDA Graphs capture a sequence of
launches once and replay them as a single unit, removing per-launch CPU cost.
torch.compile fuses ops and can use CUDA graphs automatically. Big wins for
latency-bound, launch-heavy workloads (small-batch inference).

Chain → All these tools serve one loop — what is the disciplined optimization workflow? (7.28)
Verse 7.28 — Profiling-driven optimization loop
Objective 7.4

Disciplined loop (NVIDIA APOD: Assess, Parallelize, Optimize, Deploy):
1. Assess — profile with Nsight Systems to find the biggest bottleneck (never
optimize by guessing).
2. Classify it: GPU-idle (data/comm), memory-bound, compute-bound, launch-bound.
3. Apply the matching fix (7.20–7.27).
4. Re-profile to confirm and find the next bottleneck; iterate.

Measure one change at a time; optimize the dominant cost first (Amdahl).
