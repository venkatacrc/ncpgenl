Verse 4.01 — Optimization taxonomy
Objective 4.1

Three orthogonal levers to shrink/accelerate a model: quantization (fewer bits per
weight/activation), pruning/sparsity (remove weights/structure), distillation
(train a smaller student from a larger teacher). They compose. Goals: cut memory
footprint, raise throughput/lower latency, and fit hardware acceleration paths (Tensor
Cores, sparse cores). NVIDIA's inference-optimization stack (TensorRT / TensorRT-LLM)
consumes all three.

Chain → Start with quantization — what does it mathematically do to a value? (4.02)
Verse 4.02 — Quantization: scale & zero-point
Objective 4.1, 4.2

Quantization maps floats to low-bit integers via an affine transform:

$$q=\text{round}(x/s)+z,\qquad x\approx s\,(q-z)$$

  • scale s = (x_max − x_min) / (q_max − q_min) sets resolution.
  • zero-point z is the integer that maps to real 0.
  • Symmetric quantization forces z=0 (range [−a, a]); asymmetric/affine
    allows a nonzero z (range [x_min, x_max]), better for skewed activations (e.g.
    post-ReLU). Weights → usually symmetric; activations → often asymmetric.
def quantize(x, s, z, qmin=-128, qmax=127):
    return (x / s + z).round().clamp(qmin, qmax)
Chain → One scale for a whole tensor is coarse — at what granularity should scales apply? (4.03)
Verse 4.03 — Quantization granularity
Objective 4.2

Scale/zero-point can be shared at different granularities:
- Per-tensor: one scale for the whole tensor — cheapest, least accurate.
- Per-channel (per output channel of a weight matrix): a scale per row — standard
for weights, much better accuracy at negligible cost.
- Per-group / per-block (e.g. groups of 128 weights): finest, used by GPTQ/AWQ and
low-bit (INT4) schemes to contain outliers.

Finer granularity → higher accuracy, slightly more metadata. Activations are usually
per-tensor or per-token.

Chain → Granularity aside, do we quantize only weights or activations too? (4.04)
Verse 4.04 — Weight-only vs weight+activation quantization

Objectives: 4.1, 4.2

  • Weight-only (e.g. INT4/INT8 weights, FP16 activations): shrinks memory and is
    memory-bandwidth-bound decode's friend — the decode phase is dominated by
    weight loading, so smaller weights = faster. Compute still in FP16. GPTQ/AWQ are
    weight-only.
  • Weight + activation (e.g. W8A8 INT8, FP8): also quantizes activations so the
    GEMM runs in low precision on Tensor Cores, raising compute throughput —
    essential for compute-bound prefill/large batch. Harder: activations have outliers
    (→ SmoothQuant, 4.15).
Chain → Concretely, what does INT8 quantization look like end to end? (4.05)
Verse 4.05 — INT8 quantization mechanics
Objective 4.2

INT8 = 8-bit signed integers, range [−128, 127]. On NVIDIA Tensor Cores INT8 GEMM
roughly doubles throughput vs FP16 and halves weight memory. Accuracy is preserved by
per-channel weight scales + calibrated activation scales (4.10). INT8 is the A100
fallback for FP8 workflows: same "low-precision GEMM" concept, available on Ampere.
Supported on A100 and H100.

Chain → H100 adds an 8-bit *floating* format — how does FP8 differ from INT8? (4.06)
Verse 4.06 — FP8 (E4M3 / E5M2) mechanics `[H100-ONLY]`
Objective 4.2

FP8 is 8-bit floating point with two formats: E4M3 (4 exponent, 3 mantissa —
more precision, less range; used for weights/activations) and E5M2 (5 exponent, 2
mantissa — more range, less precision; used for gradients). Unlike INT8's uniform
steps, FP8's floating format handles wide dynamic range better, so it needs less
careful calibration. Hardware: Hopper (H100) and later via the Transformer
Engine (7.13).

A100 fallback: use INT8 (4.05) or BF16 — same low-precision-GEMM concept without
Hopper FP8 units.

Chain → FP8/INT8 are 8-bit; how do the 16-bit float formats compare? (4.07)
Verse 4.07 — FP16 vs BF16 vs TF32 numerics
Objective 4.2
  • FP16: 1-5-10 (sign-exp-mantissa). High precision, narrow range → overflow/
    underflow; training needs loss scaling (7.10).
  • BF16: 1-8-7. Same exponent range as FP32 (no loss scaling needed), less mantissa
    precision. Preferred for LLM training stability. Ampere+.
  • TF32: 1-8-10 (19 bits used in Tensor Core matmul). A "free" FP32 speedup —
    FP32 storage, reduced-precision matmul. Default for torch matmul on Ampere+.

Rule of thumb: BF16 for training stability, FP16 where hardware/legacy demands,
TF32 as a drop-in FP32 accelerator.

Chain → Below 8 bits lies FP4 — what should I know conceptually? (4.08)
Verse 4.08 — FP4 / NVFP4 (Blackwell) — conceptual
Objective 4.2

FP4 = 4-bit floating point; NVFP4 is NVIDIA's Blackwell-era format pairing FP4
values with fine-grained (micro-block) scaling factors to retain accuracy at extreme
compression. Enables very high inference throughput and tiny memory footprints on
Blackwell Tensor Cores (e.g. GB200), and FP4 training via the 2nd-gen
Transformer Engine. Exam may reference it conceptually. If you have Blackwell
(sm_100), it is a real, runnable path — see Lab 4's [GB200] NVFP4 branch; on A100/H100
fall back to INT8/FP8. Contrast: INT4 (uniform) vs NVFP4 (floating + micro-scaling).

Stale-knowledge flag: NVFP4 vs MXFP4 naming and block sizes are new/unstable.
VERIFY against current docs.

Chain → Formats decided, how do we actually apply quantization after training? (4.09)
Verse 4.09 — PTQ workflow (calibration)
Objective 4.2

Post-Training Quantization: take a trained FP model, run a small calibration
dataset (a few hundred representative samples) through it to record activation
ranges, compute scales/zero-points, and convert. No retraining, fast, no labels.
Accuracy usually holds for INT8/FP8; can degrade at INT4 or on sensitive layers.
Calibration data must match the deployment distribution.

FP model -> forward calibration set -> collect activation histograms
         -> compute per-tensor/channel scales -> emit quantized model
Chain → How exactly are activation ranges chosen from those histograms? (4.10)
Verse 4.10 — Calibration methods
Objective 4.2

Choosing the clip range from activation histograms:
- Min-max: use observed min/max — simple but outlier-sensitive (one spike widens
the range, wasting resolution).
- Entropy / KL-divergence: pick the clip threshold that minimizes KL between FP and
quantized distributions — TensorRT's default for INT8; robust to outliers.
- Percentile: clip at e.g. 99.99th percentile — discards extreme tails.

TensorRT exposes these as calibrators (IInt8EntropyCalibrator2, etc.). Wrong choice →
either clipped signal or wasted range → accuracy loss.

Chain → PTQ can still lose accuracy — when must we instead train with quantization? (4.11)
Verse 4.11 — QAT workflow (fake-quant, STE)
Objective 4.2

Quantization-Aware Training inserts fake-quantize nodes (quantize→dequantize)
into the forward pass so the model learns weights robust to quantization error. The
non-differentiable rounding is bypassed in backprop by the Straight-Through
Estimator (STE) — gradient passes through as identity. Requires training data,
compute, and labels, but recovers accuracy that PTQ loses (especially at low bit-widths
or sensitive models). Usually fine-tune from a trained checkpoint.

def fake_quant(x, s, z):
    q = (x / s + z).round().clamp(-128, 127)
    xq = (q - z) * s
    return x + (xq - x).detach()   # STE: forward=xq, backward=identity
Chain → With both PTQ and QAT available, which do I pick and when? (4.12)
Verse 4.12 — PTQ vs QAT decision
Objective 4.2
PTQ QAT
Retraining none yes (fine-tune)
Data small calibration set, no labels labeled training data
Cost minutes hours–days
Accuracy good for INT8/FP8 best, recovers low-bit loss
Use when INT8/FP8, tight timeline INT4/aggressive, accuracy-critical, PTQ dropped too much

Rule: try PTQ first; escalate to QAT only if the measured accuracy drop is
unacceptable. QAT is mandatory when target bit-width (e.g. INT4) or a sensitive
model makes PTQ accuracy collapse.

Chain → For LLM weights specifically, what PTQ algorithms beat naive min-max? (4.13)
Verse 4.13 — GPTQ
Objective 4.2

GPTQ is a one-shot, layer-wise weight-only PTQ method for LLMs. It quantizes
weights column-by-column while using second-order (Hessian) information to update
remaining weights and compensate for the error introduced — minimizing output error per
layer. Enables accurate INT4/INT3 weight quantization with a small calibration set.
Weight-only → accelerates memory-bound decode; compute stays FP16.

Chain → GPTQ compensates weights; what if the *activations* are the problem? (4.14)
Verse 4.14 — AWQ (Activation-aware Weight Quantization)
Objective 4.2

AWQ observes that a small fraction of weight channels are salient (aligned with
large-magnitude activations) and dominate output error. It scales those salient
channels before quantization (protecting them) rather than keeping them in high
precision, achieving accurate INT4 weight-only quantization that generalizes across
domains without heavy calibration. Popular for LLM deployment (supported in
TensorRT-LLM).

Chain → AWQ protects salient weights; the dual problem is activation outliers — what handles those? (4.15)
Verse 4.15 — SmoothQuant (activation outlier migration)
Objective 4.2

Activations in LLMs have large per-channel outliers that make W8A8 activation
quantization hard. SmoothQuant migrates the difficulty from activations to weights
by a per-channel smoothing factor: Y = (X · diag(s)^{-1}) · (diag(s) · W). Dividing
activations by s and multiplying weights by s leaves the product unchanged but
flattens activation outliers, enabling accurate INT8 weight+activation quantization
(fast compute-bound GEMM). Complements weight-only GPTQ/AWQ.

Chain → Weights and activations aside, the KV cache is huge — can we quantize that too? (4.16)
Verse 4.16 — KV-cache quantization
Objective 4.6

At long context/large batch, the KV cache (4.26) dominates memory. Quantizing
cached keys/values to INT8 (A100-OK) or FP8 ([H100-ONLY]) roughly halves KV
memory, enabling longer context or higher concurrency, with small accuracy impact.
Trade-off: extra quant/dequant per step and possible quality loss on very long context.
TensorRT-LLM exposes INT8/FP8 KV-cache flags.

A100 fallback: INT8 KV cache demonstrates the same memory-halving concept without
FP8 hardware.

Chain → Quantization shrinks values; the other memory lever is removing weights — what is pruning? (4.17)
Verse 4.17 — Pruning: unstructured vs structured
Objective 4.1

Unstructured pruning zeros individual weights by magnitude → high sparsity but
irregular; needs specialized kernels to see speedup (dense hardware ignores the zeros).
Structured pruning removes whole units (neurons, heads, channels, layers) →
immediate dense speedup and smaller matrices, but coarser and usually needs
fine-tuning to recover accuracy. Structured is deployment-friendly; unstructured
maximizes theoretical sparsity.

Chain → NVIDIA hardware accelerates a *specific* structured sparsity pattern — which one and what does it require? (4.18)
Verse 4.18 — 2:4 structured sparsity requirements
Objective 4.1

NVIDIA Sparse Tensor Cores (Ampere A100 and later) accelerate 2:4 fine-grained
structured sparsity: in every contiguous group of 4 weights, exactly 2 must be
zero. This fixed pattern is what the hardware exploits for ~2× GEMM throughput —
arbitrary/unstructured sparsity does not qualify. Workflow: train dense → prune to
the 2:4 mask → fine-tune to recover accuracy → deploy (TensorRT). Only the 2:4
pattern gets the speedup.

Chain → 2:4 sparsity pairs powerfully with low precision — how do they combine in TensorRT? (4.19)
Verse 4.19 — Sparsity + INT8 (TensorRT)
Objective 4.1

2:4 structured sparsity and INT8 quantization stack: the Sparse Tensor Core runs an
INT8 GEMM at ~2× the dense INT8 rate, compounding memory and throughput gains. NVIDIA's
recommended workflow (per the "Sparsity in INT8" guidance): prune to 2:4, quantize
(PTQ/QAT), fine-tune to recover, then build a TensorRT engine that enables both sparse
and INT8 kernels. Verify the engine actually selected sparse+INT8 tactics (not a dense
fallback).

Chain → Beyond quantization and pruning, how do we make an entirely smaller model? (4.20)
Verse 4.20 — Knowledge distillation: teacher, student, soft targets
Objective 4.3

Train a small student to mimic a large teacher. Beyond hard labels, the student
learns from the teacher's soft targets (full probability distribution), which carry
"dark knowledge" about class similarities. A temperature T softens the teacher's
logits to expose that structure: p_i = softmax(z_i/T). Student learns far more per
example than from one-hot labels alone.

Chain → How is the distillation loss actually formed from those soft targets? (4.21)
Verse 4.21 — Distillation loss (KL + CE blend)
Objective 4.3

$$\mathcal{L}=\alpha\,T^2\,\text{KL}(p_T^{teacher}\;\|\;p_T^{student})+(1-\alpha)\,\text{CE}(y,\,p^{student})$$

  • KL term matches softened distributions (temperature T); the T² factor rescales
    gradient magnitude softened by T.
  • CE term keeps the student honest to ground-truth labels.
  • α balances the two.
import torch.nn.functional as F
def distill_loss(s_logits, t_logits, y, T=2.0, alpha=0.5):
    kl = F.kl_div(F.log_softmax(s_logits/T, -1), F.softmax(t_logits/T, -1),
                  reduction="batchmean") * (T*T)
    ce = F.cross_entropy(s_logits, y)
    return alpha*kl + (1-alpha)*ce
Chain → What real model demonstrates this, and what variants exist? (4.22)
Verse 4.22 — DistilBERT & distillation variants
Objective 4.3

DistilBERT: ~40% smaller, ~60% faster, retains ~97% of BERT's language
understanding — distilled with a triple loss (MLM + distillation KL + cosine embedding
alignment). Variant taxonomy:
- Response-based: match output logits/soft targets (4.20).
- Feature-based: match intermediate hidden states/attention maps.
- Relation-based: match relationships between layers/samples.

Distillation composes with quantization and pruning for maximum compression.

Chain → Compression handled — how do we accelerate the model on the actual GPU runtime? (4.23)
Verse 4.23 — TensorRT: builder, engine, precision flags
Objective 4.6

TensorRT is NVIDIA's inference optimizer/runtime. It ingests a model (ONNX), then
the builder applies layer/tensor fusion, kernel auto-tuning (picks fastest
tactics for the target GPU), precision selection (FP16/INT8/FP8), and memory planning,
producing a serialized engine optimized for that specific GPU. Precision flags
(FP16, INT8 + calibrator, sparsity) gate which kernels are considered. Engines are
hardware-specific — rebuild per GPU architecture.

Chain → TensorRT is general; what specializes it for transformer LLMs? (4.24)
Verse 4.24 — TensorRT-LLM: engine build workflow
Objective 4.6

TensorRT-LLM is the LLM-specialized layer on TensorRT: optimized attention kernels,
in-flight (continuous) batching (8.08), paged KV cache, tensor/pipeline
parallelism, and quantization (INT8/FP8/INT4 GPTQ/AWQ, and NVFP4 on Blackwell/GB200,
4.08). Workflow:

HF checkpoint -> convert_checkpoint.py (choose dtype/quant, TP/PP)
             -> trtllm-build (build engine, set max batch/seq, KV cache)
             -> run via TensorRT-LLM runtime or Triton TRT-LLM backend

trtllm-build) change frequently. VERIFY.

Chain → Some kernels are Hopper-specific — what plugins matter and what's the A100 fallback? (4.25)
Verse 4.25 — TensorRT-LLM plugins (Hopper-specific) `[H100-ONLY]`
Objective 4.6

TensorRT-LLM uses plugins — custom fused kernels (e.g. GPT attention plugin,
paged-KV, FP8 GEMM). Some tactics are Hopper-specific: FP8 GEMM plugins and
FlashAttention variants that exploit Hopper's TMA/WGMMA and FP8 units. The builder
selects them only on sm_90.

A100 fallback: on Ampere the builder selects INT8/FP16 fused-attention plugins
instead — same fused-attention concept, no FP8 path. Build with --dtype float16
(+ INT8) rather than FP8.

Chain → Attention plugins manage the KV cache — how big is it, exactly? (4.26)
Verse 4.26 — KV-cache memory formula
Objective 4.6

Per-token KV cache size (bytes):

$$\text{KV} = 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times \text{bytes}$$

The leading 2 = keys + values. Total = × seq_len × batch. Example: 32 layers,
32 KV heads, head_dim 128, FP16 (2 bytes) → per token = 2·32·32·128·2 ≈ 1.05 MB;
at 4096 tokens ≈ 4.3 GB per sequence. This is why long context/large batch is
memory-bound and why GQA/MQA (fewer n_kv_heads) and KV quantization (4.16) matter.

kv_bytes = 2 * n_layers * n_kv_heads * head_dim * bytes_per_elt  # per token
total = kv_bytes * seq_len * batch
Chain → If full attention is O(n²), how do we handle very long sequences cheaply? (4.27)
Verse 4.27 — Sliding-window / streaming attention
Objective 4.6

Sliding-window attention (Mistral) limits each token to attend to the last w
tokens, bounding attention cost and KV cache to O(w) instead of O(n) — enabling long
/streaming contexts. StreamingLLM keeps a few initial "attention-sink" tokens plus a
recent window to preserve stability across effectively infinite streams. Trade-off:
tokens beyond the window lose direct access (mitigated by layered receptive fields).

Chain → Quantize/prune/distill/serve covered for decoders — how are *encoders* pretrained? (4.28)
Verse 4.28 — Encoder training: masked language modeling (MLM)
Objective 4.7

Encoders (BERT) are pretrained with MLM: randomly mask ~15% of tokens and predict
them from bidirectional context. BERT's recipe: of the masked 15%, 80% → [MASK],
10% → random token, 10% → unchanged (reduces train/inference mismatch since [MASK]
never appears at inference). Contrast with decoder CLM (2.15) which predicts strictly
left-to-right.

# labels = -100 everywhere except masked positions
loss = F.cross_entropy(logits.view(-1, V), labels.view(-1), ignore_index=-100)
Chain → BERT also had a second pretraining objective — what was it and is it kept? (4.29)
Verse 4.29 — Next sentence prediction (NSP)
Objective 4.7

BERT's second objective: given sentences A and B, predict whether B truly follows A
(binary), aimed at sentence-pair tasks (NLI, QA). Later work (RoBERTa) showed NSP
hurts or is unnecessary and dropped it, training MLM-only on longer sequences with
larger batches. Exam-relevant nuance: NSP is historical BERT, not a modern
requirement.

Chain → Optimization also covers decoding-side and search knobs — what advanced sampling affects optimization studies? (4.30)
Verse 4.30 — Beam search mechanics (optimization view)
Objective 4.5

Beam search keeps the top-b partial sequences by cumulative log-prob at each step,
with length normalization to avoid bias toward short sequences:
score = (Σ log p) / len^α. Larger beams find higher-likelihood outputs (better for
translation/constrained tasks) at linear cost in b; they do not help open-ended
diversity (1.11). In optimization/ablation studies beam width is a knob whose
throughput cost must be measured against quality gain.

Chain → Beam is one knob; how does temperature figure into ablation studies? (4.31)
Verse 4.31 — Temperature scaling & ablation studies
Objective 4.5

Temperature scaling (softmax with z/T) is used two ways: as a decoding knob
(1.11) and as a post-hoc calibration method (fit a single T on a validation set so
predicted confidence matches accuracy). Ablation studies systematically remove/vary
one factor at a time (a quantization method, a sparsity level, a sampling setting) with
everything else fixed, to attribute accuracy/throughput changes to that factor. Change
one variable per run; hold seeds/decoding fixed for fair comparison.

Chain → Ablations vary knobs; how do we systematically search *training* hyperparameters? (4.32)
Verse 4.32 — Learning-rate schedules (warmup, cosine)
Objective 4.4
  • Warmup: linearly ramp LR from ~0 over the first few % of steps to avoid early
    divergence (critical for transformers/post-LN and large batches).
  • Cosine decay: after warmup, decay LR following a cosine curve to a small final
    value — the standard LLM schedule.
  • Alternatives: linear decay, inverse-sqrt (original Transformer), constant.
from torch.optim.lr_scheduler import LambdaLR
import math
def cosine_warmup(step, warmup, total):
    if step < warmup: return step / warmup
    p = (step - warmup) / (total - warmup)
    return 0.5 * (1 + math.cos(math.pi * p))
Chain → LR interacts with batch size — how do we scale them together? (4.33)
Verse 4.33 — Batch size & LR (linear scaling rule)
Objective 4.4

Linear scaling rule: when you multiply the effective batch size by k, multiply
the base LR by k (with warmup), because the gradient estimate's variance drops and
each step is more confident. Holds up to a critical batch size, beyond which
returns diminish and LR must be tempered (or use LAMB for very large batches). Effective
batch = per-device × devices × grad-accum steps (7.15).

Chain → Manual tuning is slow — how do we search hyperparameters at scale? (4.34)
Verse 4.34 — Distributed hyperparameter search
Objective 4.4
  • Grid search: exhaustive; explodes combinatorially.
  • Random search: samples the space; more efficient than grid for few important
    dims.
  • Bayesian optimization: models the objective, proposes promising points (Optuna,
    Ax).
  • Population-based training (PBT): evolves a population, copying/perturbing good
    configs during training.

Distribute trials across GPUs/nodes (Ray Tune, NeMo/Base Command). Use early stopping
(5.20) to kill weak trials fast.
