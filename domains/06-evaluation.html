The 14 Verses

Verse 6.01 — Perplexity
Objective 6.1

Perplexity is the exponentiated average negative log-likelihood — the model's
"branching factor," how surprised it is per token:

$$\text{PPL}=\exp!\left(-\frac{1}{N}\sum_{i=1}^{N}\log p(x_i\mid x_{<i})\right)=\exp(\text{mean NLL})$$

Lower = better. It is a fluency/likelihood measure computed on held-out text, not
a task-quality measure (a fluent model can still be wrong). Only comparable across models
with the same tokenizer/vocabulary (tokenization changes N). Fixed-length models use
a sliding window.

import torch

Chain → Perplexity scores likelihood, not overlap with a reference — how do we score generated text against references? (6.02)
Verse 6.02 — BLEU (n-gram precision + brevity penalty)
Objective 6.1

BLEU is precision-oriented: what fraction of the candidate's n-grams appear in the
reference (with clipping to avoid repetition gaming), geometric mean over n=1..4, times
a brevity penalty that punishes too-short output:

$$\text{BLEU}=BP\cdot\exp!\Big(\sum_{n=1}^{4}w_n\log p_n\Big),\quad
BP=\begin{cases}1 & c>r\ e^{(1-r/c)} & c\le r\end{cases}$$

c=candidate length, r=reference length. No BP → a one-word correct token would score
perfectly. Standard for machine translation; corpus-level.

Chain → BLEU measures precision — what if we care about recall (did we cover the reference)? (6.03)
Verse 6.03 — ROUGE (recall-oriented; ROUGE-N, ROUGE-L)
Objective 6.1

ROUGE is recall-oriented: how much of the reference is captured by the candidate.
- ROUGE-N: n-gram recall (ROUGE-1 unigrams, ROUGE-2 bigrams).
- ROUGE-L: based on the Longest Common Subsequence (order-aware, gaps allowed),
combined into an F-measure:

$$R=\frac{LCS(c,r)}{|r|},\quad P=\frac{LCS(c,r)}{|c|},\quad
F_{L}=\frac{(1+\beta^2)RP}{R+\beta^2 P}$$

Standard for summarization. LCS needs no fixed n and rewards in-order coverage.

Chain → BLEU/ROUGE only credit exact surface matches — how do we credit synonyms and stems? (6.04)
Verse 6.04 — METEOR (alignment, stems, synonyms)
Objective 6.1

METEOR aligns candidate↔reference words allowing exact, stem, and synonym matches
(WordNet), computes a recall-weighted F-mean (recall weighted ~9× precision), and
applies a fragmentation penalty for out-of-order chunks. Correlates better with
human judgment than BLEU at the sentence level because it credits meaning-preserving
variation. More expensive (needs stemmer/synonym resources, language-dependent).

Chain → With three overlap metrics, how do I choose among them? (6.05)
Verse 6.05 — BLEU vs ROUGE vs METEOR decision
Objective 6.1
Metric Orientation Match type Standard use
BLEU precision + brevity penalty exact n-gram machine translation
ROUGE recall (ROUGE-L = LCS) exact n-gram / subsequence summarization
METEOR recall-weighted F-mean exact + stem + synonym sentence-level, human correlation

All are surface-overlap metrics: they penalize valid paraphrases and can't judge
factuality. For semantic/quality assessment, escalate to embedding-based metrics
(BERTScore), LLM-as-a-judge (6.06), or humans (6.07).

Chain → Overlap metrics miss meaning — how do we score open-ended quality at scale? (6.06)
Verse 6.06 — LLM-as-a-judge
Objective 6.1

Use a strong LLM to score/compare outputs against a rubric (pointwise score or
pairwise preference). Scales far cheaper than humans and correlates reasonably for
open-ended quality. Known biases to control: position bias (favors first/second —
randomize order), verbosity bias (favors longer), self-preference (favors its own
family), and leniency. Mitigate with clear rubrics, reference answers, order swapping,
and calibration against human labels.

Chain → Judges still drift from ground truth — what's the gold standard? (6.07)
Verse 6.07 — Human-in-the-loop evaluation
Objective 6.1

Human evaluation is the gold standard for quality/safety: pairwise preference,
Likert-scale ratings, or task success. Requires clear guidelines, multiple annotators,
and inter-annotator agreement (Cohen's/Fleiss' κ). Expensive and slow → used to
calibrate cheaper automatic metrics and LLM-judges, and for high-stakes final
sign-off. Combine quantitative metrics + human review (NVIDIA's recommended blend).

Chain → For RAG systems specifically, which metrics apply? (6.08)
Verse 6.08 — Ragas metrics (RAG evaluation)
Objective 6.1

Ragas evaluates RAG pipelines along component-specific axes, mostly via LLM-judged
scoring:
- Faithfulness: is the answer grounded in the retrieved context (no hallucination)?
- Answer relevancy: does the answer address the question?
- Context precision / recall: did retrieval return the right, sufficient chunks?

Separating retrieval metrics from generation metrics localizes failures (bad retrieval
vs bad generation). NVIDIA integrates Ragas with NeMo/NIM endpoints (per the guide).

Chain → Metrics tell you *that* it failed — how do we find *why*? (6.09)
Verse 6.09 — Failure-mode taxonomy
Objective 6.2

Common LLM failure modes to name and detect: hallucination (fabricated facts),
repetition/degeneration (loops — decoding, 1.12), refusal/over-refusal,
instruction-ignoring, format violations, prompt-injection compliance,
reasoning errors, bias/toxicity (Domain 10), and context failures (ignoring
or misusing retrieved content). Classifying outputs into this taxonomy is the first
step of error analysis.

Chain → With a taxonomy, how do we systematically analyze errors? (6.10)
Verse 6.10 — Systematic error analysis
Objective 6.2

Process: collect a representative failure sample → label each by failure mode
(6.09) → quantify frequencies → find patterns (input length, topic, language, retrieval
miss) → form hypotheses → target fixes (data, prompt, retrieval, fine-tuning) → re-test.
NVIDIA/DLI framing: start with error analysis before adding complexity — it tells
you which lever to pull. Track error rates over time as a monitoring signal (Domain 9).

Chain → Errors localized on one platform — do results hold across hardware/platforms? (6.11)
Verse 6.11 — Benchmarking across platforms
Objective 6.3

Compare deployments (on-prem DGX vs cloud GPUs, A100 vs H100, different serving
stacks) on both quality (task metrics — must be identical given same model/decoding)
and performance (latency percentiles, throughput/tokens-per-second, cost-per-token).
Quality should match across hardware; performance differs. Control everything but the
variable under test: same model version, prompts, decoding params, batch, warmup.

Chain → Fair performance comparison needs standardization — what exactly must be fixed? (6.12)
Verse 6.12 — Standardized metrics & fair comparison
Objective 6.3

For reproducible, fair comparison: fix random seeds, decoding params (greedy for
determinism), prompt templates, dataset version, and tokenizer; report latency
percentiles (p50/p95/p99, not just mean), throughput at fixed concurrency, and confidence
intervals over multiple runs. Warm up before timing. Report the same metric definitions
across systems (e.g. TTFT vs end-to-end latency, 8.02). Standardized harnesses prevent
apples-to-oranges claims.

Chain → Ad-hoc scripts don't scale — how do we build a reusable evaluation framework? (6.13)
Verse 6.13 — Evaluation framework design (NeMo Evaluator)
Objective 6.4

A robust framework integrates: dataset/benchmark management, multiple metric types
(overlap + embedding + LLM-judge + human), standardized configs, versioned results, and
regression tracking. NeMo Evaluator is NVIDIA's tool for running standardized LLM
evals (academic benchmarks, custom tasks, LLM-as-judge) against models/endpoints. Design
for reproducibility (pinned data/seeds) and comparability (same harness across
model versions — ties to Domain 9 continuous benchmarking).

Chain → A framework must also scale to many models/large sets — how? (6.14)
Verse 6.14 — Scalable / automated evaluation harness
Objective 6.4

Automate eval as part of CI/CD and the model lifecycle: batch inference across GPUs,
parallelize LLM-judge calls, cache results, and gate releases on metric thresholds
(a failing eval blocks promotion). Integrate with the serving/monitoring stack so
production traffic can be periodically re-scored (continuous benchmarking, 9.07). Store
results with model+data+config versions for auditability. This closes the loop from
Evaluation into Deployment and Monitoring.
