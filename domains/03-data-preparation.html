The 18 Verses

Verse 3.01 — Data cleaning: dedup, normalization
Objective 3.1

Cleaning removes noise that models otherwise memorize: exact/near-duplicate documents,
inconsistent Unicode (NFC/NFKC normalization), stray whitespace/control chars, boiler-
plate, and encoding errors (mojibake). Deduplication both improves generalization and
prevents train/test leakage. NVIDIA accelerates this at scale with NeMo Curator
(3.06) on GPU (RAPIDS).

import unicodedata, re
def clean(t):
    t = unicodedata.normalize("NFKC", t)
    t = re.sub(r"\s+", " ", t).strip()
    return t
Chain → After cleaning text, what about records with missing fields? (3.02)
Verse 3.02 — Missing data & imputation
Objective 3.1

Options: drop rows/columns (safe when missingness is small and random), or impute
(mean/median/mode for tabular features; forward/backward fill for sequences; model-
based imputation). The mechanism matters: MCAR (missing completely at random) tolerates
simple imputation; MNAR (missing not at random) biases the model if imputed naively.
For text corpora, "missing" often means empty/short docs — filter by length.

import pandas as pd
df["age"] = df["age"].fillna(df["age"].median())   # robust to outliers vs mean
df = df[df["text"].str.len() >= 20]                 # drop degenerate short docs
Chain → Once complete, are numeric features on comparable scales? (3.03)
Verse 3.03 — Scaling & normalization
Objective 3.1

Standardize numeric features so no feature dominates by magnitude: standardization
z=(x−μ)/σ (zero mean/unit variance) or min-max to [0,1]. Fit scalers on train
only, then apply to val/test to avoid leakage. Mostly relevant to tabular/auxiliary
features; token embeddings are learned, not scaled. LayerNorm/RMSNorm handle
activation scaling inside the model (1.01).

from sklearn.preprocessing import StandardScaler
sc = StandardScaler().fit(X_train)     # fit on train ONLY
X_train, X_val = sc.transform(X_train), sc.transform(X_val)
Chain → Balanced scales don't fix skewed *labels* — how do we detect imbalance? (3.04)
Verse 3.04 — Class imbalance analysis & mitigation
Objective 3.1

Skewed class frequencies make a model optimize the majority and ignore rare classes;
accuracy becomes misleading (use per-class recall / macro-F1, see Domain 6). Mitigate
with resampling (oversample minority / SMOTE, undersample majority), class-
weighted loss, or focal loss. For instruction data, imbalance shows up as
over-represented task types skewing behavior.

import numpy as np, torch
counts = np.bincount(labels)
weights = torch.tensor(counts.sum() / (len(counts) * counts), dtype=torch.float)
loss_fn = torch.nn.CrossEntropyLoss(weight=weights.cuda())
Chain → Beyond labels, what does the overall feature/token distribution look like? (3.05)
Verse 3.05 — Feature distribution analysis (EDA), RAPIDS cuDF
Objective 3.1

Profile distributions before training: token-length histograms, vocabulary coverage,
language/topic mix, outliers, and correlations. On large corpora this is IO/compute
heavy — RAPIDS cuDF gives a pandas-like API on GPU for order-of-magnitude speedups
(NVIDIA's recommended tool). Length distributions directly drive max_seq_len and
padding/packing decisions (3.12).

import cudf                       # GPU DataFrame, pandas-like
df = cudf.read_parquet("corpus.parquet")
print(df["n_tokens"].describe())  # p50/p95/p99 to pick max_seq_len
Chain → Curating billions of docs by hand is impossible — what pipeline does NVIDIA provide? (3.06)
Verse 3.06 — NeMo Curator pipeline overview
Objective 3.1

NeMo Curator is NVIDIA's GPU-accelerated data-curation library for LLM pretraining/
fine-tuning corpora. Stages: download/extract → language ID → quality filtering →
deduplication (exact + fuzzy) → PII/content filtering → decontamination against
eval sets → format for training. Built on Dask + RAPIDS for multi-GPU/multi-node scale.
It is the exam's expected answer for "how does NVIDIA curate pretraining data at scale."

Chain → Within Curator, how is low-quality text separated from high-quality? (3.07)
Verse 3.07 — Quality filtering (heuristic + classifier)
Objective 3.1

Two layers: heuristic filters (document length, symbol-to-word ratio, mean word
length, fraction of alphabetic chars, repeated-line/n-gram ratios, stop-word presence)
cheaply drop junk; classifier-based filters (a small model scoring "high-quality
like reference corpus") catch subtler low-quality text. NeMo Curator ships both.
Over-filtering hurts diversity; tune thresholds against a validation sample.

Chain → Filtered text can still contain massive duplication — how is that removed at scale? (3.08)
Verse 3.08 — Deduplication: exact + fuzzy (MinHash/LSH)
Objective 3.1

Exact dedup: hash documents (e.g. document-level or via md5) and drop
collisions — cheap, catches verbatim copies. Fuzzy dedup: MinHash + LSH
estimates Jaccard similarity of shingle sets to catch near-duplicates (templated pages,
reformatted copies) without O(n²) comparison. Dedup reduces memorization, improves
generalization, and prevents eval-set contamination. NeMo Curator does both on GPU.

shingles -> MinHash signatures -> LSH bucketing -> compare within-bucket -> drop near-dups
Chain → Deduped text may still contain sensitive data — how is that handled? (3.09)
Verse 3.09 — PII redaction & content filtering
Objective 3.1

Detect and redact/replace personally identifiable information (names, emails, phone
numbers, SSNs) via regex + NER models, and filter toxic/unsafe content. Reduces
compliance risk and the chance the model regurgitates private data (ties to Safety,
Domain 10). NeMo Curator provides PII modules. Redaction must precede training; you
cannot un-train leaked PII.

import re
text = re.sub(r"[\w.+-]+@[\w-]+\.[\w.-]+", "<EMAIL>", text)
text = re.sub(r"\b\d{3}-\d{2}-\d{4}\b", "<SSN>", text)
Chain → Clean, deduped, redacted data still needs a *shape* to train on — what format? (3.10)
Verse 3.10 — Dataset formats: JSONL, prompt-completion, chat templates
Objective 3.2

Standard training formats: JSONL (one example per line), prompt-completion
pairs for SFT, and chat/messages arrays (role/content) rendered through the
model's chat template (2.01) so training matches inference formatting. Mismatched
templates between train and serve are a top silent bug. For preference data (DPO,
5.06): {prompt, chosen, rejected}.

{"messages": [{"role": "user", "content": "2+2?"},
              {"role": "assistant", "content": "4"}]}
Chain → With a format chosen, how do we split data without cheating? (3.11)
Verse 3.11 — Splits & leakage prevention
Objective 3.2

Split into train/val/test. Prevent leakage: deduplicate across splits (3.08),
split by group (user/document/time) when records are correlated, and decontaminate
training data against benchmark/eval sets (a duplicate of a test item in train inflates
scores). Fit all preprocessing (scalers, tokenizers, filters) on train only. Time-
series/production data → temporal split, never random.

Chain → Splits defined — how do we feed terabytes efficiently to the GPUs? (3.12)
Verse 3.12 — Sharding, memory-mapping & sequence packing
Objective 3.2

For large corpora: pre-tokenize to binary shards (memory-mapped) so training reads
without re-tokenizing or loading everything into RAM (NeMo/Megatron use .bin/.idx).
Sequence packing concatenates short examples up to max_seq_len to eliminate
padding waste — a major throughput win — with attention masking to prevent cross-example
attention. Shard for parallel data loading across ranks (Domain 7).

docs -> tokenize -> pack to max_seq_len -> write .bin + .idx -> mmap at train time
Chain → Both formatting and packing assume tokens exist — how are tokens produced? (3.13)
Verse 3.13 — Tokenization: subword rationale
Objective 3.3

Word-level tokenization explodes vocab and fails on OOV/rare words; character-level
gives tiny vocab but very long sequences. Subword tokenization is the compromise:
frequent words stay whole, rare words split into meaningful pieces, and any string is
representable (no true OOV). This bounds vocab size while keeping sequences short — the
basis of all modern LLM tokenizers.

Chain → What is the dominant algorithm for building subword vocab from data? (3.14)
Verse 3.14 — BPE (Byte-Pair Encoding) merge rules
Objective 3.3

BPE starts from characters (or bytes, "byte-level BPE" — GPT-2/Llama) and greedily
merges the most frequent adjacent pair repeatedly, recording an ordered merge list
until the target vocab size is reached. Encoding re-applies merges in order.
Byte-level BPE guarantees no OOV for any Unicode input. Used by GPT, RoBERTa, Llama.

init:  l o w </w>, l o w e r </w>, ...
merge most frequent pair (e.g. "l o" -> "lo"), repeat
final vocab = base chars + learned merges
Chain → BPE merges by frequency — is there an alternative that merges by likelihood? (3.15)
Verse 3.15 — WordPiece (likelihood-based)
Objective 3.3

WordPiece (BERT) also builds subwords but merges the pair that maximizes the
likelihood of the training corpus under a unigram LM, not raw frequency: it picks the
merge maximizing count(pair)/(count(a)·count(b)). Continuation pieces are marked with
## (e.g. play, ##ing). Encoding is greedy longest-match-first.

"playing" -> ["play", "##ing"]        # ## marks a non-initial subword
Chain → With two algorithms in hand, how do we choose between them (and Unigram)? (3.16)
Verse 3.16 — BPE vs WordPiece vs Unigram/SentencePiece
Objective 3.3
  • BPE: greedy frequency merges; ordered merge list; byte-level variant = no OOV.
    GPT/Llama/RoBERTa.
  • WordPiece: likelihood-maximizing merges; ## continuations; greedy
    longest-match. BERT.
  • Unigram LM: starts with a large vocab and prunes to maximize corpus likelihood;
    probabilistic segmentation. T5/ALBERT.
  • SentencePiece: a library/framework (not an algorithm) implementing BPE or
    Unigram directly on raw text (treats space as a symbol ▁), language-agnostic, no
    pre-tokenization needed.
Chain → Choosing an algorithm still leaves the vocab-size knob — how is a tokenizer trained and sized? (3.17)
Verse 3.17 — Training a tokenizer & vocab-size trade-offs
Objective 3.3

Train on a representative sample; choose vocab size. Larger vocab → shorter
sequences (fewer tokens/word, lower fertility), faster inference, but a bigger embedding
+ softmax matrix (more params/memory) and rarer tokens undertrained. Smaller vocab
→ longer sequences, more compute per document. Typical LLM vocabs: 32k–256k. Match the
tokenizer to the target languages/domains (code, multilingual need larger vocab).

from tokenizers import ByteLevelBPETokenizer
tk = ByteLevelBPETokenizer()
tk.train(files=["corpus.txt"], vocab_size=32000, min_frequency=2)
Chain → Beyond size, which tokens and edge cases decide real efficiency? (3.18)
Verse 3.18 — Special tokens, OOV & fertility
Objective 3.3

Special tokens: [CLS], [SEP], <pad>, <eos>, <bos>, chat-role markers —
must be reserved in the vocab and never split. OOV: byte-level BPE has none; other
schemes fall back to [UNK]. Fertility = average tokens per word; high fertility
(e.g. on code or an unseen language) inflates sequence length, cost, and can exceed
max_seq_len, silently truncating input. Measure fertility on your actual domain
before committing (ties to 3.05, 8.02 cost).
